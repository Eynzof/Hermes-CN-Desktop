# 消息平台扫码前流程验收

飞书和微信在扫码前都能向官方服务申请二维码，无需提供账号。原先按整项账号需求阻塞，会遗漏这些可独立验证的操作。IM-FEISHU-001 / IM-WEIXIN-001 继续负责完成扫码、配置、网关和真实收发；新增的 002 用例只覆盖扫码前流程，不替代它们。

## 实际安装版证据

- 飞书 IM-FEISHU-002 在 `runs/20260907T111109Z` 用时 10.1 秒通过：官方二维码生成、复制、手动检查 pending、重新生成、离页停止轮询、重新进入清空二维码。没有调用保存凭据命令，`.env` 摘要未变。
- 微信 IM-WEIXIN-002 同轮成功生成、解码和复制二维码，但三次状态检查分别在 15006 / 15013 / 15008 ms 超时；保留该探索记录。
- 补充脚本后，微信在 `runs/20260907T111550Z` 用时 71.0 秒完成后续取证。唯一失败断言仍是未取得正常 pending 轮询结果；两个不同二维码都从实际渲染像素解码成功（464 × 466），复制内容一致，重新生成、离页 2250 ms 无新增轮询、重入清空和配置不变均通过。

截图使用 `pngjs@7.0.0` 读取实际像素，再以 `jsqr@1.4.0` 解码并与原生命令返回的内容、真实 Windows 剪贴板三方核对。依赖均精确锁定。没有替换官方二维码接口、伪造图像或执行扫码授权。

## WIN-025：微信长轮询超时不匹配

Desktop `src/commands/im_onboarding.rs` 的共享 HTTP Client 使用 15 秒总超时，微信的 `get_qrcode_status` 也复用它。对应 Core `gateway/platforms/weixin.py` 已为二维码请求定义 35000 ms 超时。

`scripts/diagnose-weixin-poll.py` 在同一 Windows 主机向真实微信接口申请新的独立二维码，并以 45 秒上限读取状态。111550Z 的自动诊断返回：二维码生成 HTTP 200 / 156 ms；状态检查 HTTP 200 / 30133 ms / `wait`。它是服务时长诊断，不计为 Desktop 通过。

这证明官方服务能够正常回答，而 Desktop 在答案返回前结束请求。产品未修改。微信用例保留软断言失败，以便继续采集后续步骤；整项不会因后续步骤通过而变绿。

## 边界

页面没有单独的取消按钮；此处验证的是离开页面后停止新增轮询以及不落盘凭据，不声称已撤销服务端二维码。原生流程保留于当前进程内并有自身有效期。

`IM-WEIXIN-003` 单独验证页面承诺的自然过期、自动刷新和最终停止，使用真实有效期，不修改系统时间、定时器或服务响应。扫码完成、访问策略实际执行、消息投递和收发仍需要授权账号及接收者。

## 自然过期专项结果

`runs/20260907T111854Z` 的 IM-WEIXIN-003 用时 491.7 秒通过。原生命令在发起后 122.315 / 244.282 / 366.281 秒分别返回三次 `expired_refreshed`，483.459 秒返回最终 `expired`。脚本解码了初始及首次自动刷新的实际二维码像素，核对同一 flow 下的内容更新，并验证最终“已过期”提示、重新生成按钮可用和后续 4 秒无新增轮询。

本轮同时记录到 28 次已有的普通轮询错误，未调用凭据保存命令，`.env` 摘要未变。因此自然过期流程通过不撤销 WIN-025，也不代表完成了微信登录和收发。
