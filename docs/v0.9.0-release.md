# v0.9.0 发行说明与维护者运行手册

文档状态：2026-09-20，发行准备中。RC4 已完成本轮核心流程及用户人工验收；正式目标为 Desktop `0.9.0`、Core `0.21.0`、Runtime `0.21.0-cn.16`、Runtime schema `2`。**cn.16 正在准备 CI 产物，本文不表示其构建、公证、成品测试或正式发布已经通过。** 最终身份以实际 `release-record.json`、签名、摘要及运行证据为准。

## 一、面向用户的发行说明

### 更清楚的软件更新体验

v0.9.0 将日常更新集中到“软件更新”页面。底部右下角状态入口，以及“关于”“内核”中的普通更新入口，都前往同一个更新页面；内核离线时仍可打开。

- 默认接收中文社区适配的正式版。启动约 60 秒后检查，此后约每 12 小时检查一次。
- 有更新时保留底部提示；应用在前台、没有正在执行的任务或其他弹窗时显示更新提醒。
- 可以选择“查看更新”或“稍后提醒”。同一更新在稍后提醒后的 24 小时内不重复弹窗，底部入口仍保留。
- 用户点击后才下载。下载过程中可以继续使用或离开页面，也可以取消下载。
- 下载完成后由用户决定何时生效。页面按实际影响提示刷新界面、重启内核或重启应用；有受影响任务时先等待，任务结束后提醒，不自动重启。
- 更新失败时保留可查看的状态和适用的重试、恢复入口；独立组件更新不会把桌面软件版本误报为已升级。

渠道、nightly、更新源、镜像、连接测试、邀请配置、设备和凭据状态、内核与界面单独更新、已有回退及诊断能力均保留在默认收起的“高级更新选项”中。测试渠道继续遵守原有邀请和访问权限；正式渠道普通用户不需要内测邀请。切换渠道或更新源后会重新检查，切回正式渠道不会自动降级。

### 内核与可靠性改进

内核升级到 Core v0.21 系列，整合本轮社区修复，重点包括网关启动崩溃、备份遗漏聊天历史、切换档案后无法继续旧会话、澄清选择交互，以及冻结运行包的工具发现和终端资源问题。

更新流程修复了 macOS 安装后自动重启受旧单实例锁阻挡、更新日期显示异常，以及首次未保存设置时组件更新渠道不一致的问题。对话、档案与 ZIP 备份恢复等核心操作保留原有使用方式。

### 平台与签名

| 平台 | 本次发行范围与方式 |
| --- | --- |
| macOS | **最低 macOS 14**，Apple Silicon 与 Intel 分别提供安装包；正式包由 CI 完成 Developer ID 签名、公证和票据装订 |
| Windows | x64 安装包；本版不使用商业 Authenticode 证书，采用项目自有正式密钥签署 Tauri 更新包 |
| Linux | x64，提供 Debian 安装包与 AppImage；Ubuntu 22.04 为本次构建和原生内核冒烟基线 |

Windows 的更新包签名用于确认更新来源和完整性，不等同于 Windows 受信任发布者认证；首次下载安装可能出现 SmartScreen 提示。请从[官方网站](https://desktop.hermesagent.org.cn/)或[项目 GitHub Releases](https://github.com/Eynzof/Hermes-CN-Desktop/releases)取得安装包。无需导入测试根证书或关闭系统安全软件。

### 如何从现有版本升级

**使用 v0.7.0 正式版：** 收到旧版更新提醒后，前往官网下载对应平台安装包。先退出正在运行的桌面端，再覆盖安装。v0.7.0 的提醒仍然使用旧版清单，升级到 v0.9.0 后才使用新的下载与应用流程。

**使用本地 RC 或内部测试版：** 使用测试更新公钥的 RC 包无法验证正式发行密钥，请手动下载正式包并覆盖安装。已经标为 `0.9.0` 的内部包也需要手动替换，同版本不会被视为自动升级。请勿修改版本比较或关闭验签来迁移。

正常覆盖安装保留应用数据、档案、模型设置和聊天历史，**不需要卸载或删除用户数据目录**。升级前可先导出备份。若此前使用了独立 RC 测试数据目录，正式应用默认数据目录与它可能不同；保留原测试目录，通过现有 ZIP 备份导出、恢复迁移所需档案，不要直接清空或混合数据库文件。

### 验收范围说明

RC4 的 Windows 实测覆盖官方 DeepSeek 连接、真实聊天、本地文件读写、档案、ZIP 备份恢复、离页与重载后续聊、中止后续聊；另一组 RC1 → RC4 实测覆盖整包更新、取消、签名与摘要拒绝、任务等待、重启恢复和数据保留。macOS RC3 → RC4 已验证真实更新自动重启及会话、配置、草稿保留，随后用户完成人工验收。

这些记录不代表所有功能、所有平台或 cn.16 最终发行包已经全面验证。Core #136 按要求不纳入本次处理；Core #141 原始微信阻塞场景仍不在已通过范围。正式包及生产更新链路的最终结果需在发布前补齐。macOS 12 不属于本版支持范围。

## 二、维护者运行手册

本节供维护者执行发布，不能整体作为面向用户的更新弹窗文案。下列命令在 Desktop 仓库根目录的同一个 **Bash** 会话中运行。阶段之间必须先检查结果；不要一次复制执行全部公开、放量和撤回命令。

### 1. 固定输入与前置配置

| 项目 | 本次值 |
| --- | --- |
| Desktop 仓库、分支、版本 | `Eynzof/Hermes-CN-Desktop`，`release/v0.9.0-stable`，`v0.9.0` |
| Core 目标 | `runtime-v0.21.0-cn.16`，Core `0.21.0`，schema `2`；以 CI 最终记录为准 |
| 应用标识 | `cn.org.hermesagent.desktop`，保持不变 |
| GitHub 环境 | `hot-update-production` |
| 检查服务 | `https://hot-update.hermesagent.org.cn/v1/check/{{channel}}/{{target}}/{{arch}}/{{current_version}}` |
| 发行镜像 | `https://hot-update-download.hermesagent.org.cn` |
| 生产 D1 | `hermes-desktop-hot-update-production`，UUID `2709a341-5bbc-45f8-8917-dfcdfc3f59b8` |

Desktop 构建前，必须先取得 cn.16 四个平台的真实固定资产和 stable 签名清单，核对源码、Core 版本、schema 和最终下载地址。不能用 cn.14 测试包改名替代 cn.16，也不能把 Core 构建启动视作构建已通过。

GitHub `hot-update-production` 环境需提供 `HOT_UPDATE_CONTROL_ENDPOINT`、`HOT_UPDATE_MIRROR_ORIGIN` 变量。仓库或该环境需提供匹配 `tauri.conf.json` 公钥的 `TAURI_SIGNING_PRIVATE_KEY`、可选私钥密码，以及现有 Apple 签名和公证 Secrets：`APPLE_CERTIFICATE`、`APPLE_CERTIFICATE_PASSWORD`、`APPLE_SIGNING_IDENTITY`、`APPLE_API_KEY`、`APPLE_API_PRIVATE_KEY`、`APPLE_API_ISSUER`。长期发行私钥应保留安全备份，后续版本持续使用。

`windows_signing=none` 不要求 Windows 证书；选择 `authenticode` 时才要求对应证书和密码。任何模式都要求有效的 Tauri 更新签名。正式 Windows 验收环境不需要导入测试证书。

`release-desktop.yml` 通过显式 dispatch 执行，已移除 tag push 自动发布。开始前确认该 workflow 已在默认分支注册，可以从发行分支 dispatch；不要为了触发构建提前推送版本 tag。构建会固定 dispatch 的源码 SHA，已有同名 tag 必须与该 SHA 一致。

### 2. Build：仅构建最终包和私有草稿

```bash
gh workflow run release-desktop.yml \
  --repo Eynzof/Hermes-CN-Desktop \
  --ref release/v0.9.0-stable \
  -f action=build \
  -f tag=v0.9.0 \
  -f bundled_runtime_tag=runtime-v0.21.0-cn.16 \
  -f bundled_runtime_channel=stable \
  -f channel=stable \
  -f release_environment=production \
  -f windows_signing=none
```

等待该次运行完成，记录 run URL、Desktop SHA 和 Core SHA。Mac 在公证与装订后重新生成更新归档并签名；四平台汇总后核对 Tauri 签名与客户端公钥，生成 `release-record.json` 和 `checksums.txt`。所有镜像资产必须满足 480 MiB 限制。运行摘要输出 `candidate_sha256`，它是 **checksums.txt 本身**的 SHA256。

Mac 最终 `.app` 和 Linux 最终 AppImage 内的 Core 会使用独立 `HERMES_HOME` 启动，检查随包 manifest、ZIP 摘要、`/api/health` 与 `/api/version`。这项 CI 冒烟不等同于完整原生桌面界面验收。

下载草稿进行最终包验收，保留目录供后续操作：

```bash
release_dir="$(mktemp -d "${TMPDIR:-/tmp}/hermes-v090-release.XXXXXX")"
gh release download v0.9.0 \
  --repo Eynzof/Hermes-CN-Desktop \
  --dir "$release_dir"
candidate_sha256="$(shasum -a 256 "$release_dir/checksums.txt" | awk '{print $1}')"
printf '%s\n' "$candidate_sha256"
```

将此值与构建摘要比对，检查目录内所有文件均在清单内、摘要正确。验收后记录该值，后续 publish/promote 必须使用同一值；**发现文件发生变化时重新验收，不要直接接受新摘要**。不要覆盖已有草稿资产或在验收后重新构建替换它们。

最小补验包括：Mac 最终公证安装包的实际下载、安装和启动，Windows 最终 NSIS 安装与真实对话，旧 v0.7.0 覆盖升级的数据保留，正式签名更新的检查、下载、任务等待、重启和恢复；对渠道、自定义源、邀请、nightly、单独组件更新与回退做受影响范围的定向检查。视觉操作开始前通知用户。

### 3. Publish：公开同一份资产，保持 latest=false

正式包验收完成后执行：

```bash
gh workflow run release-desktop.yml \
  --repo Eynzof/Hermes-CN-Desktop \
  --ref release/v0.9.0-stable \
  -f action=publish \
  -f tag=v0.9.0 \
  -f bundled_runtime_tag=runtime-v0.21.0-cn.16 \
  -f bundled_runtime_channel=stable \
  -f channel=stable \
  -f release_environment=production \
  -f windows_signing=none \
  -f candidate_sha256="$candidate_sha256"
```

该阶段先验证已验收的全部字节，再将 Release 公开，固定 `latest=false`，随后校验 GitHub 和正式镜像的资产摘要及 Range。**latest=false 的 Release 仍然公开**。只有公开链路验证成功后，才注册和投放 D1；若验证失败，保持暂停投放，排查服务后重试同一候选。此阶段不会自动写 D1，也不会更新官网或旧 `latest.json`。

### 4. 在本地生产 D1 注册和分批投放

本机需已完成 `gh` 和 Wrangler 认证，且可以访问生产 D1。CLI 入口为 `scripts/hot-update-control.mjs`。本手册的生产命令同时传入 `--production` 和 `HERMES_ALLOW_PRODUCTION_HOT_UPDATE=1`；正常读取状态和写入都会检查该标志，修改类 `--dry-run` 也保留此检查。下面的包装函数只为单次命令设置授权标志。

```bash
production_d1='2709a341-5bbc-45f8-8917-dfcdfc3f59b8'
production_update() {
  HERMES_ALLOW_PRODUCTION_HOT_UPDATE=1 \
    node scripts/hot-update-control.mjs "$@" \
    --database "$production_d1" --remote --production
}

production_update release register-draft \
  --tag v0.9.0 \
  --channel stable \
  --mirror-origin https://hot-update-download.hermesagent.org.cn
```

注册从公开 GitHub Release 的真实 `release-record.json`、安装包和签名生成 D1 记录，初始为 `draft / 0%`。它要求正式 stable Release，不接受 GitHub 草稿或 prerelease。仅执行一次；重复注册同一 ID 会失败，不能靠删库或改 ID 绕开。若只需要核对 SQL，可在该命令末尾加 `--dry-run`，它仍会读取真实 Release 资产，但不写 D1。

从已验收记录读取四平台 ID，避免手写版本与架构：

```bash
node -e '
  const fs = require("node:fs");
  const record = JSON.parse(fs.readFileSync(process.argv[1], "utf8"));
  for (const asset of record.assets) console.log(asset.releaseId);
' "$release_dir/release-record.json" > "$release_dir/release-ids.txt"

all_releases() {
  local action="$1"
  shift
  while IFS= read -r release_id; do
    production_update release "$action" --id "$release_id" "$@" || return
  done < "$release_dir/release-ids.txt"
}

all_releases status
all_releases promote --percent 1
all_releases status
```

首次 1% 用于正式生产链路验收。测试安装 ID 预先按真实服务算法选取命中桶，但 **1% 是真实公开灰度，不是测试设备白名单**；官网与旧版清单此时仍保持原版。正式包不能伪装成 canary，现有渠道与记录唯一性规则保持不变。

`promote` 将 `draft`、`paused` 或 `published` 记录设为 `published` 并指定比例。随后根据实际检查、下载、安装启动、数据保留及用户反馈逐步放量，**每一级单独执行并核对**：

```bash
all_releases set-percent --percent 5
all_releases status
```

```bash
all_releases set-percent --percent 25
all_releases status
```

```bash
all_releases set-percent --percent 100
all_releases status
```

`set-percent` 仅适用于 `published` 记录。比例按安装 ID 与 release ID 确定分桶，不能把“某台机器没有提示”直接认定为更新失败。四个平台是独立记录，上述循环逐条执行；中途失败时先读各条状态，不能宣称整批已生效。

真实客户端连通性检查使用正确的请求头；以下请求只读取更新结果，不登记设备：

```bash
curl --noproxy '*' --fail --silent --show-error --include \
  -A 'tauri-plugin-updater/2.10.1' \
  -H 'Accept: application/json' \
  -H 'X-Installation-Id: installation-release-verification-090' \
  'https://hot-update.hermesagent.org.cn/v1/check/stable/windows/x86_64/0.8.1'
```

有资格的设备收到 200 JSON；尚无更新或未命中灰度时为 204。未提供合法安装 ID 的 401 属于访问规则，不能当作 WAF 故障。Runtime/UI 清单还需使用真实组件 UA 和 `X-Hermes-Desktop-Version: 0.9.0` 核对签名 JSON，不能仅凭 HTTP 200 判断成功；旧 v0.7.0 请求不得被分发不兼容的 v0.21 Core。

### 5. Promote：全量验收后设为 GitHub latest

确认 D1 全量投放及最终验收通过后执行：

```bash
gh workflow run release-desktop.yml \
  --repo Eynzof/Hermes-CN-Desktop \
  --ref release/v0.9.0-stable \
  -f action=promote \
  -f tag=v0.9.0 \
  -f bundled_runtime_tag=runtime-v0.21.0-cn.16 \
  -f bundled_runtime_channel=stable \
  -f channel=stable \
  -f release_environment=production \
  -f windows_signing=none \
  -f candidate_sha256="$candidate_sha256"
```

此动作再次验证相同资产和公开镜像，随后只提升 GitHub latest；它不会检查或代替本地 D1 放量。完成后将本文第一部分的正式发行说明用于 Release，依据真实资产更新 Landing 官网下载入口和旧 `latest.json`，并核对缓存后的实际返回。

旧清单不支持新服务的按设备灰度，应作为最后面向旧用户的推广动作。旧 v0.7.0 按原有启动/每日检查逻辑收到下载提示；新客户端约 60 秒首次检查、此后约 12 小时检查，还受前台、任务和稍后提醒状态影响。离线或未启动用户不会立即收到提示。

### 6. 暂停、撤回与恢复

发现影响启动、对话或数据的阻断问题，先暂停投放并读取实际状态：

```bash
all_releases pause
all_releases status
```

暂停将比例设为 0；排查确认可继续使用同一份资产后，可执行 `all_releases promote --percent 5` 重新从小范围开始。

确认该候选不能继续分发时撤回：

```bash
all_releases revoke
all_releases status
```

`revoke` 将记录设为 `revoked / 0%`，现有 CLI 不支持直接重新推广已撤回记录。发布修复版时使用新版本、独立记录和重新验收的签名资产。

暂停或撤回 D1 **不会删除用户数据、卸载已安装版本或自动降级**，也不会撤回已公开的 GitHub 资产、官网和旧版清单。若已做公开推广，需要同步停止官网推荐和旧清单通知；已安装用户按实际问题使用可用组件回退、保留数据的手动恢复或后续修复版本，不能承诺整包自动回滚。

### 7. Nightly 与最终验收记录

nightly 继续使用 `prototype` 渠道、staging 邀请和原有自签 Windows 测试身份；更新包使用与正式客户端匹配的 Tauri 发行密钥。`hot-update-staging` 的 `NIGHTLY_DESKTOP_REF` 可固定到 `release/v0.9.0-stable`，构建再固定解析出的 Desktop SHA。默认 nightly 基线为 `0.9.1`、Runtime `cn.16`；`0.9.0` 的预发布版本仍低于正式 `0.9.0`，不能作为升级目标。nightly 不成为 GitHub latest，不修改官网或旧公开清单。

截至 2026-09-20，`primelab-win` 自托管 runner（ID 22）离线。先完成本轮正式包验收，再恢复交互式、非管理员 runner，并把 `PRIMELAB_BASELINE_EXE` 指向已验收且内置正式 Tauri 公钥的安装；旧测试公钥基线无法验证新的 nightly 签名。完成这些条件前，不向默认分支注册或启用 nightly 定时任务。

恢复时显式设置 `hot-update-staging` 环境变量 `NIGHTLY_DESKTOP_REF=release/v0.9.0-stable`、`NIGHTLY_BASE_VERSION=0.9.1`、`NIGHTLY_RUNTIME_TAG=runtime-v0.21.0-cn.16`，避免旧环境变量覆盖新默认值。向 `main` 注册工作流只需同步 `.github/workflows/hot-update-nightly.yml`：prepare 检出指定发行分支，其余任务（包括恢复暂停状态的收尾任务）均检出解析出的同一 SHA；依赖与脚本从该发行版本获取。不要为注册工作流将 `main` 上未验收的业务提交合入发行分支。注册后先手动验证完整一轮，包括最后恢复 `paused / 0%`，再保留定时运行。
