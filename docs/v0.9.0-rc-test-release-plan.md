## 1. 交付目标与结论

建议制作 **`v0.9.0-rc.1` 内测候选版本**，供项目负责人在 macOS 和 Windows 上人工验收。RC1 固定本次整合后的 Desktop 和 Core 源码，保留用户软件更新体验、高级更新能力和 P0 修复。随后制作 `v0.9.0-rc.2`，验证真实候选包之间的更新及修复回归。

当前代码已具备进入 RC 制作阶段的基础；最终 RC 安装包、发行签名、内测更新服务及新包验收仍需完成。**不能把已有源码测试和旧候选包的通过记录直接作为 RC1 放行结果。**

本轮目标交付：

1. 可直接安装的 macOS Apple Silicon 和 Windows x64 RC1。
2. 内置 Core 0.21.0 系列、完整资源和可追溯的版本信息。
3. 面向测试设备可用的更新入口，以及后续 RC2 的实际下载、生效和恢复流程。
4. 简明安装说明、人工测试清单、已知问题清单和完整证据索引。

沿用当前操作范围：先在本地及已授权的 Windows 主机准备和验收。GitHub 预发布、远程更新服务写入、push 和 CI/CD 属于后续分发执行阶段，本计划书本身不执行这些操作。RC 不进入 stable 全量渠道，不修改 Landing 和正式官网更新清单。

| 对象 | 计划值或分配规则 |

| Runtime 发行版本 | 分配未使用的 `0.21.0-cn.N`；冻结时核对所有已使用候选编号与分发记录，禁止复用 cn.12／cn.13 等历史测试编号 |
| UI 组件版本 | 沿用现有独立版本规则，确保候选严格递增，同时记录 Desktop 来源提交和兼容范围 |
| RC 更新渠道 | 使用现有 `canary`，保留 beta、prototype／nightly 现有映射和权限 |

根 `package.json` 是 Desktop 版本源，执行 `pnpm version:sync` 后检查 Cargo、Tauri、workspace、构建版本常量和打包文件名。RC 不能只改下载文件名或 tag；运行中的应用也必须显示实际 RC 版本。平台安装器内部版本映射需在真实升级流程中验证。

已经交付的 RC 产物保持不可变。产品代码、资源或签名后的字节变化都产生新的候选版本和摘要；不得覆盖同名 RC 包后继续沿用旧报告。

### 3.2 当前内部 0.9.0 的迁移问题

SemVer 顺序为 `0.9.0-rc.1 < 0.9.0-rc.2 < 0.9.0`。因此现有内部测试包 `0.9.0` 不会把 RC1 识别为更高版本。Tauri 默认更新比较也要求候选版本更高。[SemVer 规范](https://semver.org/lang/zh-CN/)、[Tauri 更新版本比较](https://v2.tauri.app/plugin/updater/#allowing-downgrades)。

处理方式：

- 本机现有内部 0.9.0 保留；RC1 先安装在独立验收环境，复制或导入测试数据。
- 同 identifier 的包不能假定可在默认应用目录安全共存。独立环境使用明确的安装路径、应用数据根和 HERMES_HOME；日常实例与测试实例分开启动。
- 若专门验证内部 0.9.0 的替换安装，在有备份的隔离环境执行，记录为“内部版本迁移”，不计作自动升级成功。
- 不为 RC 修改产品的防降级比较器，也不把正式版本号提前改成 0.9.1 来绕过问题。
- RC1 → RC2 用两个真实构建的包完成，不能只改服务端清单版本。

### 3.3 内测准入和默认体验

新建 RC 测试环境内置 canary 渠道和经过验证的更新地址。需要设备准入时提供一次性邀请配置，使用现有导入功能和系统凭据库；测试人员不需要手填 endpoint、deviceId 或令牌。

已有配置优先级保持原规则。已有用户显式选择的 stable、自定义源和凭据不被安装器覆盖；测试环境加入 canary 通过明确的邀请导入或已有高级入口完成。普通页面显示“当前接收测试版更新”。

“没有发布候选更新”必须返回正常的无更新状态；服务不可达、未授权和版本不适用应有对应反馈，不能一律显示“已经是最新版本”。

## 5. 构建与产物计划

### 5.1 平台优先级

| 批次 | 平台 | 目的与要求 |
| --- | --- | --- |
| 首批，RC1 必须交付 | macOS Apple Silicon | 供用户主要人工验收；本机原生构建，DMG 和更新包均验证 |
| 首批，RC1 必须交付 | Windows x64 | 在 SSH 别名 `windows`、192.168.50.2 上原生构建和验证；GUI 使用交互式桌面会话 |
| 第二批 | macOS Intel／macOS 12 | 需要对应构建及运行环境；旧 WebKit Markdown 兼容必须在实际最低支持系统验证 |
| 第二批 | Ubuntu 22.04 x64 | 需要对应 Linux 环境；使用 22.04 构建基线并验证最终运行包 |

首批标注“两平台 RC”，不把尚未验收的平台列为支持已验证。Intel／Linux 缺口不阻止这两平台的小范围人工测试，但阻止宣称全平台正式版验收完成。现有正式流水线按四平台汇总，首批本地交付使用逐平台产物清单，保留正式汇总校验。

### 5.2 构建顺序

1. **冻结输入。** 从上述起始提交建立 RC 准备快照，完成必要版本和构建配置修改，再记录最终双仓 SHA；冻结后不追随移动的 main、latest 或上游新提交。
2. **先构建 Core。** 使用 Python 3.14 和锁定依赖；生成该平台的冻结执行器、Node/TUI、Dashboard、skills、plugins、tools 和其他必需资源。
3. **验证冻结 Core。** 直接运行冻结执行器，检查工具发现、网关启动、cron Python worker、Node/PTy、MCP stdio 和依赖导入。Windows 必须确认 OpenConsole.exe／winpty-agent.exe 存在并可用。
4. **签名 Core 并固定清单。** macOS 正规化 framework/symlink 并签名；使用最终 ZIP 的摘要、真实源码 SHA 和最终下载地址生成 schema 2 签名清单。签名后不再更换 artifactUrl。
5. **组装 Desktop。** stage 同一 Core 提交对应的 Dashboard、插件和技能；明确内置 Runtime tag／manifest 渠道；在编译时设置非空的 RC 更新配置。
6. **构建与签名平台包。** Windows 生成安装器和更新资产；macOS 完成 Developer ID、公证、装订，并对最终更新 tar 包重新签名和计算摘要。遵循仓库已有公证流程及 [Apple 公证文档](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)。
7. **安装核验。** 从最终交付包安装，核对 App/EXE、实际 Core `/api/version`、`runtime/current.json`、UI 构建标识、签名和资源来源。
8. **生成交付清单。** 收集完成签名、公证和装订后的文件，最后计算 checksums；后续不修改这些文件。

现有脚本优先复用：`sync-desktop-version.mjs`、`stage-bundled-runtime.mjs`、`stage-dashboard-web-dist.mjs`、技能／插件 stage、平台 bundled build、`collect-release-artifacts.mjs` 和 `finalize-release-record.mjs`。根据实际本地输入补齐缺项，不将发布工作流里的上传步骤直接在本地重放。

### 5.3 交付物

- macOS ARM64：可安装 DMG、实际 `.app.tar.gz` 更新包及 `.sig`。
- Windows x64：可安装 NSIS EXE、对应更新资产及 `.sig`。
- 两平台 Core ZIP、签名 manifest；UI 独立更新包及签名清单。
- `checksums.txt` 与逐平台 release record：Desktop/Core SHA、Runtime 编号、组件版本、大小、摘要、渠道、构建工具版本、签名结论。
- `RC-TEST-GUIDE.md`：安装、加入内测、人工操作顺序、恢复旧环境的方法。
- `RC-KNOWN-ISSUES.md`：确认存在的问题、影响平台、规避方式、是否阻断测试。
- `RC-ACCEPTANCE.md`：必测项结果、原始证据链接及放行结论。

上述测试指南与报告随执行生成。文件名、大小、下载地址和摘要以构建后真实结果为准。

## 6. 更新服务准备和可见范围

正常链路使用现有受允许的内测域名和 canary 设备准入机制。需要核实检查服务、资产下载服务和组件 manifest 三者分别可用，不能只证明首页能访问。

执行顺序：

1. 固定候选资产的最终地址，上传资产后逐项核对大小、摘要和下载行为；需要 Range 的下载路径核对 206。
2. 核对检查服务、镜像及必要的源站读取权限，保证测试设备能得到完整资产。
3. 登记 release record 为 draft／0%，校验 Desktop/Core 版本和目标平台映射。
4. 给明确测试设备配置 canary 准入，使用既有发布状态与百分比规则开放该候选；0% 本身不应被误认为测试设备已能收到更新。
5. 在未加入内测的设备请求上验证 RC 不可见；stable 和其他渠道原有行为保持不变。
6. 演练 pause／revoke，验证“已检查”和“已下载”两种状态在应用前都重新核对候选资格。

远程内测服务操作进入执行阶段时再完成；本地 HTTPS 故障夹具继续用于错误签名、断网、撤回和失败恢复。完整的正常联网更新验收使用真实可信 TLS 和正常准入，不要求用户长期安装测试 CA、配置 hosts 或代理。

正式服务上次报告的问题只作为待复核项，不能用旧记录断言当前仍故障，也不能仅凭代码已有默认 URL 宣称服务已恢复。

## 7. 测试方案

### 7.1 原则与环境

- 本轮自动化只跑 **新整合修复、软件更新和直接受影响的流程**。复用既有脚本；发现失败后只重跑修复对应范围，不反复执行全套。
- Windows 使用现有 `e2e/native-windows/`；macOS 使用 `e2e/native-macos/`，补齐尚未自动化的原生操作。
- 测试在最终安装包中执行。允许测试进程开启现有自动化访问，但提供给人工验收的默认启动方式不暴露调试端口。
- 真实对话默认使用用户已授权的 DeepSeek 官方 `deepseek-v4-flash`。密钥沿用独立测试环境配置，不写入计划书、仓库或交付包。
- 工具、数据库、Core 和桌面进程真实运行；模型调用以实际会话和 Token 记录为证。确定性服务用于 MCP 协议和更新故障注入，单独标注。
- 视觉验收开始前先通知用户。先观察并确认关键操作，再固化为脚本；不把仅有截图或页面可打开记为业务通过。
- 更新失败、进程中止和数据恢复使用隔离测试数据；人工日常环境先保留可恢复备份。

| 源与渠道切换 | 清除旧检查；已下载包重新核对；切回 stable 不降级；普通/高级互斥 | 持久化计划和执行锁 |
| 异常与恢复 | 签名/摘要失败、撤回、403、断网、安装失败、UI 挂载超时、旧 UI 缓存 | 原始错误、恢复后的版本和可用性 |
| 数据与外部 Core | 草稿、页面、配置、历史保留；外部 Core 不被本机更新流程停止或升级 | 前后快照、数据摘要、外部 PID |

12 小时周期和 24 小时同版本免打扰边界使用针对性时钟测试验证，并在人工试用期间观察实际行为；不通过改产品间隔缩短 RC 的真实体验。更新断网恢复按当前实现验证，不预先承诺尚未实现的断点续传。

### 7.3 必须区分的升级路径

| 路径 | 方式及结论边界 |
| --- | --- |
| 已有正式版 → RC1 | 以实际存量包为基线，验证覆盖安装；旧版本确实支持相应更新机制时才另测自动升级 |
| 0.8 内部 RC → RC1 | 核对旧 Core 与新兼容矩阵的迁移、运行资源和数据保留 |
| 已有内部 0.9.0 → RC1 | 隔离环境的手动替换／数据导入，不计作自动升级 |
| RC1 → RC2 | 两平台必须验证完整自动发现、下载、用户确认生效和更新器重启 |
| RC1 仅更新 Core／UI | 独立组件路径，不同时投放整包候选，以免整包优先级覆盖组件测试 |
| RC → 正式 0.9.0 | 正式版最终包产生后补验；RC 阶段不制作或投放伪装正式版来提前宣称完成 |

需检查旧内部热更 UI 使用的版本是否高于 RC 的内置 UI；迁移应实际验证旧缓存不会覆盖新 RC 界面，不通过清空所有用户数据掩盖问题。

### 7.4 人工验收安排

建议用户按以下顺序验收，工程侧同步保存必要证据：

1. 安装和首次运行：约 10～15 分钟。检查版本、冷启动、现有数据和关键入口。
2. 日常任务：约 30～45 分钟。完成真实中文对话、停止续聊、档案往返、文件和终端任务、澄清选择、一个 cron 或子任务。
3. 软件更新体验：约 20～30 分钟。查看 RC2 提醒、稍后提醒、下载期间继续工作、有任务等待、确认生效、核对重启后的原会话。
4. 高级选项：约 15～20 分钟。展开渠道与邀请配置、连接测试、组件详情和适用回退；确认普通用户无需理解内部术语即可完成更新。
5. 实际使用观察：建议 24～48 小时，观察重启、休眠唤醒、历史续聊和重复提醒；报告时间是建议观察窗口，不是已经完成的测试。

这里的时间是人工操作估算，不包含包下载、公证排队或复杂任务运行时间。

### 7.5 自动化收尾与报告

Windows 继续使用 `scripts/run.ps1 -Case ...` 定向执行和 `-Remaining` 同基线续跑。制作 RC 专项清单，将现有 RUNTIME-001～004 与本次 P0 对应的已有工作流关联；新增交互先核对现有用例再扩展，避免重复编号。

macOS 当前脚本已覆盖启动、快照和夹具，UI 操作尚未全部无人值守。RC 阶段优先固化更新页、下载、应用、重启、版本核实和历史续聊，报告明确区分“人工原生通过”和“脚本原生通过”。

每个运行保留产物摘要、Desktop/Core/UI 版本、实际进程路径、脚本快照、操作记录、结果及失败附件。零自动重试，失败不覆盖；脚本问题与产品缺陷分开记录。修改过产品或产物后建立新基线，不能把旧包的绿色结果合并计入新 RC。

现有 101 项目录的历史分组为 89 项必需流程、4 项既有豁免、8 项隐藏功能。本轮只形成 RC 专项覆盖报告；如后续需要声称“新 RC 全功能完整验收”，必须在该精确包基线上补齐对应全部必需项。

## 8. 缺陷处理、回退与放行标准

### 8.1 问题分级

- **P0：停止分发候选。** 网关／应用无法启动、聊天历史或配置丢失、更新后无法恢复使用、错误平台或不兼容包被应用、错误停止外部 Core。
- **阻断 RC 的 P1：修复并重建。** 常用聊天／档案／备份不可完成、更新主流程卡死、任务保护失效、签名或准入错误、更新结果与实际版本不符。
- **非阻断问题：列入已知问题。** 边缘 UI 缺陷或有明确规避方式的低频场景；标明影响、复现步骤及复测安排，不能默认为已解决。

源台账的未关闭 Issue 需要按“是否在本 RC 复现、是否影响必测流程”复核；不是要求 RC 前关闭全部历史需求。Core #136 继续按既有要求跳过；Core #141 原始微信阻塞场景、外部账号收发及最低平台兼容缺口继续单列。已有外部消息投递豁免不因发布 RC 自动取消。

### 8.2 失败处理

1. 停止向测试设备提供有问题的候选，保留失败包、签名和证据。
2. 区分检查／下载失败、应用前拒绝、组件切换失败和整包安装失败，核实当前实际运行状态。
3. 组件按已有机制恢复上一份可用版本；整包使用已保存的可安装候选及备份恢复，准确报告恢复到了哪个版本。
4. 不承诺任意安装中断都能完整回滚目录或数据。跨版本数据恢复前核对格式兼容性，避免用旧程序直接打开不兼容的新数据。
5. 修复后发布新 RC 编号，定向复测失败流程及直接关联的升级／数据保护路径。

### 8.3 分阶段门槛

| 门槛 | 通过条件 | 通过后允许做什么 |
| --- | --- | --- |
| A：本机功能预验收 | 固定源码可构建、基础签名/校验可信、可安装启动、P0 路径通过、数据隔离 | 项目负责人使用本地候选检查功能；缺少发行条件时明确标注，不能宣称可分发 RC |
| B：RC 小范围交付 | 两平台最终签名产物通过；macOS 公证完成；canary 正常联网更新可用；主链路无 P0／阻断 P1；说明和恢复材料齐全 | 将 RC 交给明确测试人员持续试用 |
| C：RC 更新能力通过 | RC1→RC2、组件更新、高级能力和失败恢复在实际包上通过；人工体验认可 | 结束 RC 更新专项，进入更广覆盖或正式版收尾 |
| D：正式版放行 | 最终平台矩阵、签名、公证、存量用户升级和正式服务通过；正式渠道投放及停发方案就绪 | 单独安排 v0.9.0 正式发布及用户更新提示 |

RC 通过不等于所有存量用户马上收到更新。旧客户端是否具备主动检查和新 Modal 能力必须逐版本核实；没有相应能力的旧客户端仍需要兼容提示入口或手动安装。正式版发布时另行处理这部分迁移。

## 9. 工作安排与预计耗时

以下按“已具备两台构建机、发行签名与内测服务权限可用、没有新 P0”的假设估算，不作为固定交付日期。依赖未满足时记录具体阻塞，保持可独立开展的工作推进。

| 阶段 | 工程工作 | 交付／决策点 | 估算 |
| --- | --- | --- | --- |
| 第 1 阶段 | 核对签名和服务前置条件、固定版本与新 Runtime、补齐 RC 构建输入 | 可复现构建清单和阻塞列表 | 0.5～1 个工作日 |
| 第 2 阶段 | 两平台 Core 与 Desktop 构建、签名、公证、打包 smoke | RC1 最终安装包和 checksums | 1～2 个工作日，可并行构建 |
| 第 3 阶段 | 安装／P0／更新专项自动化，准备真实 RC2，完成两平台升级 | 可交付 RC 测试材料和失败记录 | 约 1 个工作日 |
| 第 4 阶段 | 用户人工验收和 24～48 小时使用观察；工程定向修复并迭代 RC | 人工结论、新 RC 或正式版收尾清单 | 1～2 天观察，修复时间视问题而定 |

在前置条件齐全的情况下，首批两平台 RC1 可按 **2～3 个工作日**安排；完整 RC1→RC2 更新专项和人工反馈按 **3～5 个工作日**安排。公证排队、签名材料、更新服务开通或新发现 P0 会延长时间。Intel／Linux 第二批单独安排，不隐含已有设备或构建权限。

工程侧负责版本冻结、构建、脚本、证据和缺陷修复；用户负责产品体验和实际工作任务的验收判断。每阶段汇报实际构建编号、阻塞项和下一项可验证结果。

## 10. 开始执行时的首批动作

1. 记录正式签名、公证和内测服务前置条件的可用状态，并核对远程发行编号，确定未占用的新 Runtime 版本。
2. 从已整合双仓 SHA 准备 RC1，同步真实应用版本，更新 cn.4 旧构建输入，核实实际更新配置。
3. 先产出 macOS ARM64 和 Windows x64 Core 及安装包，完成签名、冻结资源和冷启动验收。
4. 在视觉验收前通知用户，交付可安装包、测试指南及明确的已知问题。
5. 准备真实 RC2，执行自动提醒、任务等待、组件和整包更新、失败恢复及原会话续聊，形成 RC 放行报告。
