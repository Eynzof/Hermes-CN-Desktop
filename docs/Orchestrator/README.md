# 多 Agent Orchestrator 场景库

> 状态：第一版角色与人工编排模板
>
> 适用入口：Hermes CN Desktop 多 Agent 群聊
>
> 最近验证：2026-07-23

本目录把群聊测试中使用的角色原型整理成可复用的多 Agent 编排方案。它解决三个问题：

1. 用户应该创建哪些 Profile；
2. 每个 Profile 应承担什么职责、输出什么、禁止做什么；
3. 用户应如何通过多轮 `@成员` 把独立意见组织成可验收的结果。

这些文档是“人工编排模板”，不是自动 Orchestrator 引擎。当前版本仍由用户发送每一轮消息，Agent 不会自动点名下一个 Agent，也不会在后台自行接力。

## 1. 从测试角色到通用角色

确定性 E2E 和真实模型测试使用了以下 Profile：

| 测试 Profile | 通用角色 | 处理方式 |
|---|---|---|
| `qa-planner` / `qa-real-planner` | `planner` | 保留“方案、假设、退出条件”职责 |
| `qa-critic` / `qa-real-critic` | `critic` | 保留“反例、遗漏、风险”职责 |
| `qa-synthesizer` / `qa-real-synthesizer` | `synthesizer` | 保留“引用各方观点后形成结论”职责 |
| `qa-failing` | 无用户角色 | 仅用于故障注入，禁止作为业务模板 |

测试角色使用 `qa-` 前缀，是为了便于隔离环境识别和清理。用户创建正式 Profile 时应使用场景文档给出的稳定 ID，不要复用 `qa-failing`。

## 2. 当前群聊编排契约

设计编排时必须以真实运行语义为准：

| 契约 | 对编排的影响 |
|---|---|
| 普通消息或 `@all` 触发全部成员 | 不希望参与本轮的主持人或裁判必须被排除，改用明确的多成员 mention |
| 多个 `@成员` 按房间成员顺序串行回复 | 房间成员顺序应与期望的稳定展示顺序一致 |
| 同一轮成员基于同一个回合前快照独立回答 | 同轮不能形成“提案者说完，批评者立即阅读并反驳”的接力 |
| 下一轮能看到已经完成的历史 | 评审、修订和总结必须拆成后续轮次 |
| 房间状态只存在于当前 Core 进程 | 长任务应及时导出结论，不能把群聊当成跨重启持久存储 |
| 当前没有群聊专用上下文压缩 | 长轮次要控制输入、引用和中间产物长度 |

典型的可靠流程是：

```text
准备输入与验收标准
  → 第 1 轮：多个专家基于同一快照独立作答
  → 第 2 轮：审查者读取上一轮并指出证据缺口
  → 第 3 轮：原作者针对审查结果修订
  → 第 4 轮：主持人引用历史并形成最终结论
  → 用户按验收标准检查、导出和归档
```

若两个成员必须互相回应，就必须拆成两个用户回合。把两者同时写在一条消息里，只会得到两个互相独立的回答。

## 3. 角色卡设计标准

每个可复用角色至少要写清以下字段：

| 字段 | 要回答的问题 |
|---|---|
| 稳定 ID | 用户在群聊中如何 `@` 它 |
| 单一职责 | 它在这一阶段只负责什么 |
| 输入契约 | 它可以使用哪些材料和哪些前序成员发言 |
| 输出契约 | 输出必须包含哪些结构化字段 |
| 证据规则 | 哪些结论必须引用来源、日志行或历史发言 |
| 禁止行为 | 它不能决定、不能执行或不能泄漏什么 |
| 交接条件 | 什么结果完成后，用户可以触发下一角色 |
| 失败判据 | 出现什么就应判定本轮无效并重试 |

创建新角色时从[角色卡模板](./role-card-template.md)开始，不要只写“你是一名专家”。角色名称不同但职责、输入和输出完全相同，不构成有效的多 Agent 分工。

## 4. 六类典型编排

| 编号 | 场景 | 核心角色 | 推荐轮数 | 主要产物 |
|---|---|---|---:|---|
| O-01 | [多专家独立会诊](./01-expert-consultation.md) | 领域专家、风险专家、主持人 | 2～3 | 决策备忘录 |
| O-02 | [方案—红队—决策](./02-plan-red-team-decision.md) | 提案者、红队、决策者 | 4 | 修订方案与决策记录 |
| O-03 | [不同模型 A/B 对比](./03-model-ab-comparison.md) | 模型 A、模型 B、裁判 | 2～4 | 可复核评分表 |
| O-04 | [研究—核查—编辑](./04-research-fact-check-edit.md) | 研究员、事实核查员、编辑 | 3～5 | 带出处的成稿 |
| O-05 | [隔离代码库只读 Review](./05-readonly-code-review.md) | 架构师、平台专家、QA | 3～4 | 风险与回归矩阵 |
| O-06 | [脱敏日志故障复盘](./06-incident-retrospective.md) | 运维分析员、安全审查员、负责人 | 3～4 | 事故复盘与行动项 |

选择模式时先看最终决策由谁承担：

- 需要多个平行专业判断：使用 O-01；
- 需要明确反驳和修订闭环：使用 O-02；
- 需要比较模型而不是比较人格：使用 O-03；
- 需要证据经过核查后才能成稿：使用 O-04；
- 需要保证工作区无副作用：使用 O-05；
- 需要从时间线收敛到根因和行动项：使用 O-06。

## 5. Profile 配置约定

### 5.1 命名

- 使用小写英文和连字符，例如 `risk-reviewer`；
- ID 表达职责，不绑定具体人员或供应商；
- 显示名可使用中文，但 mention 以稳定 ID 为准；
- 测试 Profile 才使用 `qa-` 前缀；
- 不把模型名写进通用角色 ID，模型 A/B 场景除外。

### 5.2 描述

Profile 描述用于成员栏快速识别，应控制为一句话：

```text
负责找出方案中的反例、遗漏和不可逆风险，不替提案者重写方案
```

描述不是完整约束。详细人格、输入输出契约和禁止行为应放进对应 Profile 的 `SOUL.md` 或等价角色指令。

### 5.3 模型与工具

- 独立会诊应按专业能力选择模型，不要求所有成员相同；
- A/B 对比必须记录 Provider、模型 ID、参数和 Profile 版本；
- 只读 Review 只开放读取、搜索和只读 Git 能力；
- 事实核查需要网络时，必须保存来源 URL 和访问时间；
- 安全、运维和评审场景默认禁止外部写入；
- 任何场景都不得把 API Key、Token、Cookie 或个人信息写入提示词。

## 6. 建群与执行检查单

### 建群前

- [ ] 每个 Profile 只有一个清晰职责；
- [ ] 角色说明包含输出格式和禁止行为；
- [ ] 房间成员顺序符合预期展示顺序；
- [ ] 输入已经脱敏，工作区已经隔离；
- [ ] 已定义最终产物和判定通过的标准；
- [ ] 已确定哪些轮次必须使用定向 mention。

### 每轮发送前

- [ ] 本轮目标成员集合明确；
- [ ] 需要读取其他成员意见的角色被安排在后续轮次；
- [ ] 提示词说明可使用的历史范围；
- [ ] 输出要求可观察、可复核；
- [ ] 不包含与本轮职责无关的执行授权。

### 结束前

- [ ] 最终结论引用了必要的前序证据或观点；
- [ ] 冲突、假设和未知项没有被静默抹平；
- [ ] 行动项包含负责人、完成条件和验证方式；
- [ ] 只读场景已复核文件校验和及 Git 状态；
- [ ] 结论已导出到可持久化位置；
- [ ] 已记录模型、Profile 版本、房间成员顺序和执行时间。

## 7. 验证状态

本目录中的角色分工来自已经执行的群聊 E2E 与真实模型四轮协作测试，但不能据此宣称六种模板都已完整验证。

当前已验证的公共能力包括：

- 定向单成员和多成员路由；
- 多成员按房间顺序回复；
- 同轮独立、下一轮可读取历史；
- planner → critic → planner → synthesizer 四轮上下文连续；
- 单成员失败时后续成员继续。

已关闭的产品缺陷和仍未执行的场景记录在[TODO](./TODO.md)。完整测试证据与用例矩阵见[《多 Agent 群聊：用户场景与测试指南》](../group-chat-usage-and-test-guide.md)。

## 8. 维护规则

- 场景文档只描述已支持的人工作流，不把未来的自动接力写成当前能力；
- 修改角色职责时同时更新输入、输出、禁止行为和验收标准；
- 产品功能缺陷留在测试指南中编号，角色模板只引用，不把缺陷包装成限制；
- 新增场景前先判断是否能由现有角色组合完成，避免为同一职责创建近义角色；
- 自动化或导入格式落地后，Markdown 仍作为人类可审查的规范来源。
