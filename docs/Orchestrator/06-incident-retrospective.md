# O-06：脱敏日志故障复盘

## 1. 适用目标

从脱敏日志和已知事件中先重建时间线，再独立检查安全影响，最后形成根因、促成因素和可验证行动项。

本模式面向复盘，不用于实时执行生产操作。Agent 不得重启服务、修改配置、封禁账号或发送事故通知。

## 2. 房间配置

**建议房间顺序：**

```text
ops-analyst
security-reviewer
incident-lead
```

三名成员不能在第一轮一起回答。安全审查需要读取时间线，负责人需要读取前两名成员的结果。

## 3. 输入准备

进入群聊前完成脱敏：

- API Key、Token、Cookie、Authorization header；
- 邮箱、手机号、身份证件和真实姓名；
- 内网地址、主机名、数据库连接串；
- 客户数据、消息正文和受限业务字段；
- 能反推出敏感值的 URL query 或错误堆栈参数。

使用稳定占位符保持关联，例如：

```text
[USER-01]
[HOST-02]
[TOKEN-REDACTED]
[ORDER-17]
```

不要把每次出现的同一实体替换成不同占位符，否则无法重建事件关联。脱敏映射应保存在群聊之外的受控位置。

## 4. 角色卡

### `ops-analyst`

**Profile 描述：**

```text
从脱敏日志重建事件时间线，区分观测事实、推断和未知项
```

**核心指令：**

```text
你是运维分析员。只基于提供的脱敏日志重建时间线。
每个事件必须引用日志文件、行号或稳定事件 ID，并标记为“事实 / 推断 / 未知”。
识别首个异常、影响扩散、检测、处置和恢复时间。
不猜测缺失日志，不执行任何生产操作。
```

### `security-reviewer`

**Profile 描述：**

```text
复核时间线中的越权、泄漏和审计风险，不重复输出可能的敏感值
```

**核心指令：**

```text
你是安全审查员。读取脱敏日志和 ops-analyst 的时间线。
检查身份、权限、数据暴露、横向移动、日志完整性和响应流程风险。
引用事件 ID，不复述疑似凭证或个人信息；发现未脱敏内容时只报告位置和类型。
区分“已确认安全事件”“需要排查”和“未发现证据”。
不执行封禁、轮换或通知动作。
```

### `incident-lead`

**Profile 描述：**

```text
综合运维与安全证据，形成根因、促成因素、未决问题和有负责人的行动项
```

**核心指令：**

```text
你是事故负责人。只在运维和安全审查完成后形成复盘。
分别引用 ops-analyst 和 security-reviewer 的具体发现。
明确区分根因、促成因素、影响和仍待验证假设。
行动项必须包含负责人角色、优先级、完成条件、验证方式和截止条件。
不把“重启后恢复”自动当作根因，不执行行动项。
```

## 5. 事件记录格式

为每条日志预先分配稳定事件 ID：

| 字段 | 内容 |
|---|---|
| `event_id` | 例如 `EVT-0012` |
| 时间戳 | 包含时区和精度 |
| 来源 | 服务、主机或日志文件占位符 |
| 级别 | INFO / WARN / ERROR 等 |
| 脱敏正文 | 不含秘密值 |
| 原始位置 | 文件名和行号 |
| 完整性 | 完整 / 截断 / 缺失区间 |

跨服务时间戳可能存在时钟偏差。若没有同步证据，时间线必须标记误差范围。

## 6. 编排步骤

### 第 1 轮：时间线

```text
@ops-analyst

基于提供的脱敏日志重建时间线。
输出：
1. 首个已知正常点；
2. 首个异常；
3. 影响扩散；
4. 检测、处置和恢复事件；
5. 每一步对应的 event_id；
6. 事实、推断和未知项；
7. 日志缺口与时钟偏差。

禁止执行任何命令或生产操作。
```

### 第 2 轮：安全审查

```text
@security-reviewer

复核上一轮时间线和原始脱敏日志。
输出：
- 已确认的安全事实；
- 需要排查的越权、泄漏或审计风险；
- 未发现证据的风险；
- 未完全脱敏内容的位置和类型；
- 需要补充的日志或审计记录。

只引用 event_id，不复述疑似敏感值。
```

### 第 3 轮：负责人总结

```text
@incident-lead

综合 ops-analyst 和 security-reviewer 的结果，输出：
1. 影响范围；
2. 已确认根因；
3. 促成因素；
4. 已排除解释；
5. 未决问题和验证方法；
6. 行动项表；
7. 复核日期。

必须分别引用两名成员的具体发现。
没有充分证据时，把根因写为“待确认”，不要强行收敛。
```

### 可选第 4 轮：证据更新

如果新增日志改变结论：

```text
@ops-analyst @security-reviewer

新增脱敏证据：[填写]
请各自只说明它改变了哪些 event_id、判断或未知项。
```

两名成员同轮独立复核后，再让 `incident-lead` 更新复盘版本。

## 7. 行动项契约

| 行动项 ID | 类型 | 关联证据 | 负责人角色 | 优先级 | 完成条件 | 验证方式 | 截止条件 |
|---|---|---|---|---|---|---|---|

行动项类型至少区分：

- 立即缓解；
- 根因修复；
- 检测改进；
- 恢复与演练；
- 安全跟进；
- 文档或流程。

“加强监控”“提高稳定性”不是合格行动项，除非有可观察的完成条件。

## 8. 验收与失败判据

### 通过

- 时间线每一步可追溯到 event_id；
- 事实、推断和未知项被明确区分；
- 安全成员不重复输出潜在敏感值；
- incident-lead 分别引用运维和安全发现；
- 根因与“恢复动作”没有混淆；
- 每个行动项都有负责人角色和验证方式。

### 失败

- 日志缺口被模型自行补全；
- 把时间相关性直接写成因果关系；
- 安全审查重复显示凭证或个人信息；
- 没有证据却断言不存在安全影响；
- 行动项没有完成条件；
- Agent 实际执行了生产变更、外部通知或凭证轮换。

## 9. 保存与审计

- 群聊不是事故管理系统或合规审计日志；
- 最终复盘应保存到受控、可版本化的位置；
- 保存脱敏版本、输入哈希、双仓 SHA、Profile 和模型版本；
- 原始日志和脱敏映射按组织安全策略单独保管；
- 若群聊出现未脱敏信息，应停止继续输入并按安全流程处理，不在更多轮次中重复它。
