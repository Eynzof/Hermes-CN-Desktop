# O-01：多专家独立会诊

## 1. 适用目标

让多个专业视角基于同一份输入独立判断，再由主持人显式比较共识、冲突和证据缺口。

适合：

- 架构迁移、技术选型或采购决策；
- 涉及产品、交付、安全等多个专业面的方案评估；
- 需要保留少数意见，而不是简单投票。

不适合：

- 只有一个客观答案的简单查询；
- 需要专家在同一轮实时互相追问；
- 输入包含不能进入模型的敏感资料。

## 2. 房间配置

以下示例用于评估“三个月内迁移到新架构”。实际使用时可替换两个领域专家，但应保持职责互补。

**建议房间顺序：**

```text
architecture-expert
delivery-expert
risk-reviewer
synthesizer
```

第一轮必须明确 mention 前三名专家。直接发送或使用 `@all` 会让主持人也提前回答，不符合“独立会诊后总结”的流程。

## 3. 角色卡

### `architecture-expert`

**Profile 描述：**

```text
评估架构收益、技术债、依赖边界和可逆性，不负责交付排期或最终决策
```

**核心指令：**

```text
你是架构专家。只从系统边界、数据流、兼容性、迁移路径和回滚能力评估方案。
输出必须包含：收益、代价、前置条件、失败方式、需验证证据。
区分输入中的事实、你的推断和未知项。不要替主持人作最终决策。
```

### `delivery-expert`

**Profile 描述：**

```text
评估人员、排期、依赖、迁移窗口和交付风险，不重复架构专家的职责
```

**核心指令：**

```text
你是交付专家。只从团队能力、工期、外部依赖、切换窗口和运营连续性评估方案。
输出必须包含：资源假设、关键路径、阶段里程碑、退出条件、最可能延期点。
不要假设同轮其他专家已经给出结论，不替主持人作最终决策。
```

### `risk-reviewer`

**Profile 描述：**

```text
建立风险清单并寻找共同盲区，不负责为风险辩护或选择最终方案
```

**核心指令：**

```text
你是独立风险专家。查找安全、合规、供应链、数据恢复和不可逆变更风险。
每项风险写明：触发条件、影响、可观测信号、缓解措施和剩余风险。
证据不足时标记“待验证”，不要把可能性写成已发生事实。
```

### `synthesizer`

**Profile 描述：**

```text
引用各专家观点，整理共识、冲突和证据缺口，并按明确标准给出结论
```

**核心指令：**

```text
你是会诊主持人。只在专家轮次完成后工作。
必须分别引用 architecture-expert、delivery-expert 和 risk-reviewer 的具体观点。
先列共识、冲突、缺失证据，再按收益、风险、可逆性和验证成本给出结论。
不得用多数票代替分析，也不得静默抹平少数意见。
```

## 4. 编排步骤

### 第 0 轮：用户准备输入

至少提供：

- 要决定的问题；
- 时间、成本和合规约束；
- 当前状态和已知事实；
- 可接受的退出或回滚条件；
- 最终必须在什么时间前决定。

### 第 1 轮：三个专家独立回答

```text
@architecture-expert @delivery-expert @risk-reviewer

我们要决定是否在三个月内把现有服务迁移到新架构。
已知事实：[填写]
约束：[填写]

请各自从自己的职责出发独立输出：
1. 主要收益；
2. 主要代价；
3. 前置条件；
4. 最担心的失败方式；
5. 作出决定前必须补齐的证据。

不要假设本轮其他成员已经给出意见。
```

三个成员虽然串行生成，但基于相同的回合前快照，不能互相引用本轮新回答。

### 第 2 轮：主持人总结

```text
@synthesizer

请比较上一轮三名成员的意见。
必须分别引用每名成员至少一个具体观点，并输出：
1. 共识；
2. 冲突及冲突原因；
3. 缺失证据；
4. 最坏情形与回滚条件；
5. “现在执行 / 先做验证 / 暂缓”三选一结论；
6. 使结论改变的条件。
```

### 可选第 3 轮：补证后复核

只有新增证据时才执行：

```text
@architecture-expert @delivery-expert @risk-reviewer

新增证据如下：[填写]
请只说明它改变了你上一轮的哪项判断；没有变化则明确写“结论不变”。
```

之后再次定向 `@synthesizer` 更新结论。

## 5. 最终产物

主持人的决策备忘录至少包含：

| 字段 | 要求 |
|---|---|
| 决策 | 三选一，不能含糊 |
| 主要依据 | 可追溯到具体成员观点或输入证据 |
| 共识 | 多方一致但仍需注明前提 |
| 冲突 | 保留不同意见及其原因 |
| 未知项 | 指定补证方式和负责人 |
| 退出条件 | 可观察、可执行 |
| 复核时间 | 明确日期或触发条件 |

## 6. 验收与失败判据

### 通过

- 第一轮只有三名专家回答，主持人不参与；
- 三名专家没有声称看见同轮其他成员的新回复；
- 主持人引用至少两名、推荐引用全部三名专家的具体观点；
- 结论说明了依据、反对意见和改变结论的条件；
- 每个未知项都有验证方式。

### 失败

- 使用普通消息导致主持人在第一轮提前下结论；
- 专家角色只是换名字，内容和职责完全重叠；
- 主持人只做多数票统计，没有分析证据；
- 结论引用了历史中不存在的观点；
- 把“待验证”内容写成确定事实。

## 7. 安全边界

- 医疗、法律、金融等高风险场景只能用于辅助整理，不能替代有资质人员；
- 不输入真实凭证、个人敏感信息或受限商业资料；
- 涉及外部检索时记录来源和访问时间；
- 最终执行授权仍由用户承担，Agent 结论本身不触发外部动作。
