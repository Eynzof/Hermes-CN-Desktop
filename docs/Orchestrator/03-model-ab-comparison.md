# O-03：不同模型 A/B 对比

## 1. 适用目标

让两个模型在相同任务、相同角色指令和相同输入下独立回答，再用统一量表比较能力、成本和风险。

这个模式比较的是模型配置，不是两个不同人格。A、B 的角色说明和可用工具必须保持一致。

## 2. 房间配置

**建议房间顺序：**

```text
model-a
model-b
judge
```

| Profile | 配置要求 |
|---|---|
| `model-a` | 模型 A；使用公共评测角色指令 |
| `model-b` | 模型 B；使用与 A 字节等价的角色指令和工具 |
| `judge` | 固定第三个模型；只按预先定义的量表评分 |

第一轮使用 `@model-a @model-b`，不能直接发送，否则 `judge` 也会提前回答。

## 3. 角色卡：公共候选

`model-a` 和 `model-b` 除 Provider、模型 ID 和待比较的模型参数外，其他配置应一致。

**Profile 描述：**

```text
在固定输入和输出契约下完成候选任务，用于模型对比，不评价其他候选
```

**公共核心指令：**

```text
你是模型对比中的候选执行者。
只完成用户给定任务，不评价其他候选，不猜测自己或他人的模型身份。
明确区分事实、推断和未知项；需要来源但无法核实时，必须标记。
严格遵守本轮指定的输出结构和长度限制。
```

## 4. 角色卡：裁判

### `judge`

**Profile 描述：**

```text
按预注册量表比较候选回答，引用具体证据，不按文风或模型品牌投票
```

**核心指令：**

```text
你是模型回答裁判。只使用预先给定的量表，不自行修改权重。
每项评分必须引用候选回答中的具体内容，并区分事实错误、遗漏和表达偏好。
若无法验证正确性，标记“不可判定”，不得用流畅度代替真实性。
输出单项评分、证据、总分、置信度和可能的顺序偏差。
```

## 5. 评测前注册

发送任务前先在测试记录中固定：

| 字段 | 示例 |
|---|---|
| 任务版本 | `task-2026-07-23-v1` |
| 输入哈希 | 输入文件或文本的 SHA-256 |
| Provider / 模型 | A、B、judge 的完整 ID |
| 参数 | 温度、最大 token、推理配置 |
| 工具 | 两候选必须相同 |
| Profile 版本 | 公共角色指令版本 |
| 评分维度 | 正确性、完整性、可执行性、幻觉风险 |
| 权重 | 例如 40 / 25 / 20 / 15 |
| 顺序 | 房间成员顺序和第二轮是否交换 |

不记录这些信息，就不能把差异归因于模型。

## 6. 编排步骤

### 第 1 轮：候选独立回答

```text
@model-a @model-b

任务版本：task-2026-07-23-v1
任务：[填写]
已知输入：[填写]
输出必须包含：[填写]
禁止使用：[填写]

两名候选独立回答，不评价另一名候选。
```

### 第 2 轮：群聊内弱盲评

```text
@judge

请按预注册量表比较上一轮 model-a 和 model-b 的回答。
每个维度必须引用具体内容，并输出：
- A、B 单项得分；
- 支持得分的证据；
- 事实错误或不可判定项；
- 加权总分；
- 置信度；
- 可能的顺序或显示名偏差。
```

群聊历史携带 sender，因此这不是严格匿名评审，只能称为“弱盲评”。裁判看得见 `model-a` 和 `model-b` 的身份标签。

### 第 3～4 轮：交换顺序复测

新建一个房间，把成员顺序改为：

```text
model-b
model-a
judge
```

保持任务、公共角色、参数和评分量表不变，再执行一次。若裁判结论随顺序变化，必须记录顺序偏差，不能只保留对目标模型有利的一次。

## 7. 严格匿名方案

若必须让裁判不知道候选身份，不能直接依赖同一个群聊历史。使用以下流程：

1. 在只包含 `model-a` 和 `model-b` 的房间收集回答；
2. 由测试工具或用户把回答复制为 `回答一`、`回答二`，移除 sender、模型名和可识别措辞；
3. 随机化顺序并保存映射，映射不提供给 `judge`；
4. 在 judge-only 会话中评分；
5. 评分完成后再解盲。

匿名化过程不得修改回答正文。若发生清理或截断，必须保存原文、匿名版和变换记录。

## 8. 输出契约

| 维度 | 权重 | A 得分 | B 得分 | 证据 | 不可判定项 |
|---|---:|---:|---:|---|---|
| 正确性 | | | | | |
| 完整性 | | | | | |
| 可执行性 | | | | | |
| 幻觉风险 | | | | | |

额外记录：

- 首 token 和总耗时；
- 输入、输出 token；
- 失败或重试次数；
- 估算成本；
- 工具调用次数；
- 裁判置信度；
- 顺序交换后的结果。

## 9. 验收与失败判据

### 通过

- A、B 的任务、角色指令、工具和输入一致；
- 每个候选各有一个正确 sender 的独立气泡；
- judge 只在候选完成后的下一轮回答；
- 每项评分引用具体内容；
- 完整记录 Provider、模型 ID、参数和顺序；
- 交换顺序后保留全部结果。

### 失败

- 用群聊输入框的单一模型选择器假设覆盖所有 Profile；
- A、B 使用不同人格或不同工具，却把差异归因于模型；
- 声称群聊内 judge 是严格匿名；
- 裁判按文风或品牌偏好评分；
- 只运行一次或只报告有利结果；
- 在日志中打印 API Key。
