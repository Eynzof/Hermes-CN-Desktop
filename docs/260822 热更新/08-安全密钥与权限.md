# 08. 安全、密钥与权限

## 1. 必须区分的密钥

| 凭据 | 用途 | 客户端是否内置 | 泄漏影响 |
|---|---|---:|---|
| Tauri updater 私钥 | 给最终安装包生成 detached signature | 否，只内置公钥 | 可伪造被客户端信任的更新，最高严重度 |
| Windows Authenticode 私钥/证书 | 证明 Windows 发布者、建立 SmartScreen 信誉 | 证书信息可见，私钥不可见 | 可签冒充发布者的 Windows 程序 |
| Apple Developer ID / notarization 凭据 | macOS 签名、公证 | 证书链可见，私钥不可见 | 可签/提交冒充发布者的 macOS 应用 |
| Runtime/UI manifest 私钥 | 给独立 Runtime/UI 包签名 | 否，只内置公钥 | 可伪造对应轨道更新 |
| 设备 token | 允许单台设备检查/下载某个 ring | 否 | 可下载内测包，但仍不能伪造签名 |
| Cloudflare 发布 token | 上传 R2、写 D1、部署 Worker | 否 | 可改发布状态或物料，应按能力拆分 |

TLS、设备 token、Tauri 签名和操作系统代码签名解决不同问题，不能共用一把“万能密钥”。

## 2. 原型密钥现状

- staging Tauri 私钥在仓库外：`~/.codex/secrets/hermes-hot-update-staging/updater.key`，权限为 600。
- 对应公钥已嵌入本工作树 `tauri.conf.json`。
- 原型私钥无密码，只允许 staging；这本身是**正式发布阻塞项**。
- Windows 测试机上的临时私钥已删除；设备 token 目前是用户级环境变量。
- D1 只保存设备 token 的 SHA-256，不保存明文。
- 原型 Windows 安装包只有 Tauri updater 签名，没有 Authenticode。

正式环境必须生成全新的 production Tauri 密钥对，不能把 staging 私钥“升级”为生产私钥。

## 3. 推荐密钥边界

```text
构建身份：只能读源码、写 draft R2 前缀
OS 签名身份：只能调用对应平台签名，不可 promotion
Tauri 签名身份：只读待签文件、输出 .sig，不可写 D1
验证身份：只读 draft artifact，可安装 prototype
发布身份：只能把已验证 release 从 draft 改为 published/调整比例
暂停身份：只能 pause/0%，任何值班人员可用
部署身份：可部署 Worker/migration，不拥有签名私钥
```

“暂停”权限应比“发布”权限更容易取得；事故时不应等待唯一管理员上线。

## 4. 生产密钥存储

优先级：硬件/托管签名服务或 HSM > 隔离签名机 + 系统 Keychain > 受保护 CI secret。不要把原始私钥作为普通文件复制到每个平台 runner。

具体要求：

- Tauri 私钥至少有强密码，密码与私钥分开保管。
- 签名节点不执行来自 PR 的任意脚本；只接受已验证 hash 的二进制输入。
- 所有签名记录输入 SHA、输出签名 SHA、调用身份、源 SHA、审批号和时间。
- Cloudflare API token 按 R2 upload、D1 promotion、Worker deploy 拆成不同 token。
- 优先使用 CI OIDC/短期凭据，避免长期账户级 token。
- production 和 staging 使用不同账户资源、域名、D1、R2 前缀和公钥。

## 5. 设备 token

### 生成

- 使用密码学安全随机数，至少 256 bit。
- 一设备一 token；禁止一个“内测群通用密码”。
- D1 只写 token SHA-256，原值只交付一次。

### 客户端保存

- Windows：Credential Manager/DPAPI。
- macOS：Keychain。
- Linux：Secret Service；不可用时明确提示风险，不静默落普通 JSON。
- 原型环境变量方案仅限专用测试机。

### 生命周期

- 邀请、ring 调整、禁用、轮换都写审计日志。
- 最近访问时间只用于运营和异常发现，不作为唯一安全判定。
- 离职、设备遗失、token 出现在日志/截图时立即 disable 并换新。

## 6. 控制面安全

当前 Worker 只有客户端读取路由，管理通过受控 Wrangler/D1 操作。这比在原型期匆忙开放管理 API安全，但不适合多人生产运营。

生产管理面应具备：

- Cloudflare Access/服务令牌保护；
- 角色：viewer、publisher、emergency-pauser、infra-admin；
- 状态迁移白名单和双人批准；
- 每次 promotion 自动检查 R2 HEAD、完整 SHA、Tauri signature、metadata 和兼容矩阵；
- append-only 审计输出到独立存储；
- D1 定期导出，R2 inventory 和恢复演练；
- 对 release key 永不覆盖，撤销只改状态不篡改历史记录。

## 7. 供应链安全

- Desktop/Core 必须固定源 SHA，构建单不可写 `latest`。
- 锁定 pnpm、Cargo、Rust、Tauri、NSIS 和 Runtime manifest 版本。
- 从网络预热的工具核对官方哈希；缓存不是信任源。
- R2 上传后从远端完整回读 SHA，而不是只相信上传命令成功。
- 操作系统签名后再做 Tauri 签名；Tauri 签名后任何字节变化都应让验证失败。
- 发布响应中的 Core/Runtime metadata 来自构建物料，不允许运营人员随手填写。
- 后续加入 SBOM、依赖漏洞扫描和可复现性对照，但不要让扫描替代签名与真实安装测试。

## 8. Tauri 公钥轮换

客户端内置公钥，因此不能直接把服务端签名钥匙换掉。安全轮换采用桥接版本：

1. 用旧私钥签一个 Desktop 桥接版 `R`，其中嵌入新公钥；
2. 所有旧客户端仍只获得由旧钥签名的 `R`；
3. `R` 及以后客户端才获得新钥签名的版本；
4. 控制面按当前客户端版本选择旧钥桥接包或新钥正常包；
5. 旧钥和桥接路径保留到旧客户端支持期结束，再正式销毁旧钥。

紧急泄漏而没有桥接版时，无法在不信任旧钥的前提下远程更新旧客户端；只能停止更新并通过官网/人工安装一个新信任根版本。这也是私钥保护的核心理由。

## 9. 事故处置

### 怀疑发布包有缺陷

暂停 release → 比较 R2 SHA/签名/源 SHA → 判断是否只是功能缺陷 → 制作前向修复 → canary。

### 怀疑设备 token 泄漏

禁用单设备 → 查访问时间/IP 粗粒度记录 → 新 token → 不需要更换 Tauri 签名钥。

### 怀疑 Tauri 私钥泄漏

立即暂停所有使用该信任根的发布 → 隔离签名系统 → 保全审计 → 启动公钥轮换/人工恢复预案。仅删除 R2 文件不足以解决问题。

### 怀疑 Cloudflare 发布 token 泄漏

吊销 token → 暂停发布 → 核对 Worker 版本、D1 状态和 R2 inventory → 轮换最小权限 token。由于攻击者不能生成 Tauri 签名，客户端仍应拒绝伪造包，但可能遭遇拒绝服务或合法旧包重放，仍需严肃处理。

## 10. 隐私和日志

只收集发布诊断所需字段：匿名设备 ID、release ID、平台/架构、阶段、错误类别、时间和客户端版本。不要上传聊天内容、Hermes 配置、路径、用户名、token、Authorization header 或完整 IP 历史。日志留存期和访问权限应在 beta 前明确。
