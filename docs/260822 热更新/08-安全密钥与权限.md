# 08. 安全、密钥与权限

## 1. 四种独立信任

| 身份 | 作用 | 泄漏影响 | 必须分离 |
|---|---|---|---|
| Tauri updater 私钥 | 证明 updater 字节由项目授权 | 可签恶意更新，最高风险 | staging/production 分离；不授予 D1 权限 |
| Windows/macOS 代码签名身份 | OS 发布者、公证和时间戳 | 可冒充发布者 | staging/production/商店按政策分离 |
| GitHub Release 发布身份 | 创建/上传/发布资产 | 可替换未受保护候选或制造 Release | 与 promotion 审批分离 |
| Cloudflare D1/Worker 身份 | 部署控制面、写发布状态 | 可扩大灰度或拒绝服务 | deploy、staging control、production control 分离 |

任何单一 job 不应同时拥有 production Tauri 私钥、OS 代码签名和 production promotion 权限。

## 2. 客户端设备 token

- `device create` 生成 32 字节随机 token；D1 只存 SHA-256。
- 一次性邀请 artifact 最多保留 1 天，通过受控渠道交给测试用户。
- 导入后 token 存 OS credential store，service 为 `cn.org.hermesagent.desktop.hot-update`。
- `update-config.json` 只保存 endpoint、channel、device ID 等非密钥。
- token 只作为控制 Worker Bearer；下载前客户端清空所有 Update headers。
- stable installation ID 是随机灰度键，不是认证 token。

## 3. GitHub Environment

`hot-update-staging` 可由内测负责人审批；`hot-update-production` 必须配置更严格审批人、禁止 self-review，并保护 secrets/vars。

staging 也不得保持无保护状态。PR 真机测试前至少配置：

- required reviewer；只有一名 reviewer 时不要同时开启 prevent self-review，否则触发者无法自批。
- 当前 `hot-update-staging` 按仓库所有者决定保留 **Allow administrators to bypass configured protection rules**。本轮自动化不得使用该入口，仍须留下 required reviewer 的批准和 deployment 记录；这是仅限 staging 的已接受风险，不是 production 配置建议。
- deployment branches/tags 使用 Selected branches and tags。
- PR 测试按事件的 `GITHUB_REF` 放行 `refs/pull/<PR>/merge`，合并后 Nightly 另行放行 `main`。

`hot-update-production` 在创建时仍应关闭管理员绕过。若未来决定保留，必须单独做生产风险评审，不能因为 staging 的例外自动沿用。

PR workflow 必须使用 `pull_request`、同仓 head 和精确 head SHA；禁止用可从未受信任 head 取代码并持有密钥的 `pull_request_target`。

production 管理 CLI 还要求 `HERMES_ALLOW_PRODUCTION_HOT_UPDATE=1`。这只能防误触，真正授权仍由 Environment、GitHub repository permissions 和 Cloudflare token scope 提供。

截至 2026-08-23，staging 已配置专机 device token、匹配当前 updater 公钥的 Tauri 私钥、只供专机 Nightly 使用的自签名 Windows PFX，以及人工创建的 `CLOUDFLARE_API_TOKEN`。PR 三包 workflow 已通过 required reviewer 正常使用 Tauri/PFX 身份，没有使用管理员绕过；D1 管理仍由本地 staging CLI 完成，因此 Cloudflare token 的 Actions D1 Edit 权限仍待默认分支管理工作流先做只读验证。

Cloudflare 的 D1 token 以 Account 为资源边界，不能只限定到单个 D1 数据库。当前 production D1 尚未部署；未来如需对 staging/production 做凭据级硬隔离，应使用独立 Cloudflare Account，而不是仅依赖不同 token 名称。production Environment 和全部 production 身份均未创建。

## 4. 发布供应链

- 所有构建输入固定到 Desktop SHA、Core SHA、Runtime tag；禁止 `latest`。
- 先完成 Authenticode/codesign/notary，再对最终 updater 字节做 Tauri 签名。
- 平台 job 不能直接创建 Release；四平台聚合成功后才创建 draft。
- 发布后从 GitHub 和 Cloudflare 各完整回读，核对 SHA/大小/Range/签名。
- D1 注册 CLI 不接受人工 SHA/size/signature/Core version。
- GitHub tag 和版本化资产不可覆盖；修复用更高版本号。

## 5. Worker 安全

- 控制接口 no-store；restricted ring 必须 token/ring 一致。
- 下载 Worker 固定 GitHub hostname/repo/tag/path，拒绝 query、凭据、嵌套路径和 percent 编码绕过。
- 下载域不接收/转发 Authorization 或 Cookie。
- updater 最大 480 MiB。
- 控制 Worker 校验 D1 中 mirror URL 必须等于配置的固定 mirror origin。
- 401/403/404、签名和格式错误不触发 GitHub 回退，避免把策略或完整性故障伪装成网络问题。

## 6. 审计与隐私

`release_events` 保存操作人、workflow URL、动作和前后状态。`client_update_events` 只收最小字段，不收聊天、配置、路径、完整错误栈或 token。

建议保留期：

- release 审计：至少 1 年。
- 客户端聚合事件：90 天后聚合/删除明细。
- 一次性邀请 artifact：1 天。
- Nightly 构建证据：14 天；稳定发版 provenance/checksums 随 Release 长期保留。

## 7. 事件处置

### 功能缺陷

立即 pause/0% → 核对已安装范围 → 生成更高版本前向修复 → 从 prototype 重走。

### SHA/签名异常

立即 revoke → 停止 promotion → 保全 GitHub/D1/Workflow 证据 → 核对最终字节和签名顺序。不得回退到另一份“看起来能装”的资产。

### Tauri 私钥疑似泄漏

暂停所有使用该信任根的候选 → 隔离签名系统 → 评估公钥轮换和人工恢复。删除缓存或 GitHub 文件不能撤销已经泄漏的签名能力。

### Cloudflare token 泄漏

吊销最小权限 token → 暂停 promotion → 核对 Worker versions 和 release_events → 换 token。Tauri 签名仍应阻止伪造包，但攻击者可能拒绝服务或重放合法旧包。

## 8. 禁止项

- token/私钥/PFX 写入 repo、D1、release record 或应用日志。
- 用 production 私钥跑 nightly。
- 允许 PR 代码在持有 production secret 的未审批 job 中执行。
- 关闭 Tauri 签名验证来“验证网络”。
- 为清缓存删除宽泛目录或覆盖同 tag 资产。
