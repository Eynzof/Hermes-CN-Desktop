### 6.1 启动环境事实

- SSH 直接启动 GUI 落在 Session 0，WebView2 返回 `0x80070578`（无效窗口句柄），不能用于完整 CDP smoke。
- 将临时计划任务放到 Session 1 后 WebView2 正常；但 `RunLevel=Highest` 会让 WebView2 忽略本机 CDP flag。改成 `Interactive + Limited` 后端口 9222 才稳定出现。
- 专用 `Hermes GitHub Actions Runner` 最终已改为 `Session 1 / Interactive / Limited`，runner 22 在 GitHub 复核为 online、idle。Nightly 和启动脚本已增加 Session 0/提升权限 fail-fast。

### 6.2 主下载和安装

真实应用完成 `.7.1.1 → .7.1.2`：

```text

fallbackUsed = false
```

smoke 在旧进程退出后重新连接新 CDP，证明不是只下载或手工覆盖；detached helper 完成 NSIS、显式重启和新版本检查。Runtime source commit、artifact SHA、revision 9 均保持，9120 正常。

### 6.3 GitHub 回退与大陆网络边界

第一轮在目标 FRA 边缘确认镜像精确资产返回 `503 + CF-Cache-Status: BYPASS + x-hermes-staging-fault: 503`，客户端随后连接 GitHub Release CDN `185.199.110.133:443`。但测试机无代理直连 1 MiB 仅约 `60,051 B/s`，完整下载约 40 分钟后以 `error decoding response body` 失败，没有 pending、没有安装。这证明 GitHub 直连不是大陆加速方案，也证明当前无断点续传会浪费整包流量。

为只验证客户端逻辑，随后建立仅绑定测试机 loopback 的临时 SSH 反向代理：GitHub 1 MiB 约 `498,476 B/s`。用 hosts 精确阻断 staging 下载域、保持控制域可达，让客户端触发网络错误并经代理直连同一 GitHub 固定 tag。最终结果：

```text
manifestSource = cloudflare-control
downloadSource = github-release
fallbackUsed = true
Desktop = 0.8.1-prototype.592.7.1.2
Runtime/Core/sentinel = 与主链路一致
```

该结果证明“网络类错误 → GitHub → 同签名安装”代码正确；不能把它表述为大陆无代理 GitHub 下载成功。测试后 hosts 标记行和反向隧道均已精确删除。

### 6.4 拒绝、暂停和鉴权

- 404：冷路径故障响应在 Windows 边缘确认为 404/BYPASS；客户端返回 `Download request failed with status: 404 Not Found`，`fallbackUsed=false`。
- 坏签名：客户端返回 `Invalid encoding in minisign data`，`fallbackUsed=false`，baseline 未变且没有 pending。
- 错 token：客户端 `updateAvailable=false` 并停止在控制面；Tauri 2.10.1 把原始状态包装成通用 `Could not fetch a valid release JSON`，独立 HTTP 复核为 401。状态码透传是诊断改进项，不是授权绕过。
- pause：candidate 先完整下载、验签并产生 pending，随后 D1 pause/0%；安装前复核返回 `当前没有获准安装的更新`，`installStarted=false`，helper 未启动。

版本化缓存的故障注入也暴露一个操作边界：精确 URL 一旦在该边缘 HIT，响应可能在 Worker 执行前返回。每次负向测试必须用冷 tag/资产，并在目标机先核对 `x-hermes-staging-fault`，不能只看 deploy 成功。
