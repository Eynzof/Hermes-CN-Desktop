# 01. 通俗说明与当前卡点

## 1. 我们到底需要什么

把热更新想成一套“只给登记用户送达、能验明真伪、发现问题能立即停发”的快递系统，一共需要六样东西：

1. **包裹**：Windows/macOS/Linux 的安装包，里面明确带的是哪一版 Desktop、Core 和 Runtime。
2. **封条**：Tauri updater 私钥给安装包签名；客户端只内置公钥，签名不对就拒绝安装。
3. **收件人名单**：每台内测设备有自己的 `device_id`、令牌和 ring；没有登记或令牌失效就看不到清单和文件。
4. **分拣规则**：按 `prototype → canary → beta → stable` 分组，再按 0/5/25/100% 灰度。
5. **仓库与调度台**：R2 保存安装包，D1 保存设备/发布状态，Worker 回答“这台机器现在能不能拿到这个版本”。
6. **流水线和刹车**：提交后自动测试、构建、签名、上传为草稿；人工批准后才发布。出问题时立刻暂停清单和下载，再发一个修复版。

专用 Windows 机器 `primelab-win` 负责真实 Windows 编译和安装测试。Mac 或隔离签名节点只负责使用 Tauri 私钥签名，避免把私钥长期放在 Windows 构建机上。

## 2. 现在已经有什么

### 已实现并实测

- Desktop `0.8.x` ↔ Core/Runtime `0.20.x` 的兼容矩阵已经进入代码、Rust、前端和构建检查。
- Tauri 官方 updater 已接入现有“一键更新”入口，支持动态 staging 端点、Bearer 设备令牌、下载进度、签名校验和 Windows passive 安装。
- Cloudflare staging 的 Worker + D1 + R2 已建立，能做设备鉴权、ring、百分比灰度、清单下发、带 Range 的安装包下载和一键暂停。
- Windows 从基线版检查、下载、验签、安装、退出、自动重启到最终版本确认已经完整走通。
- 暂停发布后，旧版设备得到 `204 No Content`，安装包入口得到 `404`；已升级设备不会被强行降级。

详细证据见[原型实测记录](./10-原型实测记录.md)。

## 3. 现在真正的卡点是什么

当前已经不是“代码能不能更新”的卡点，而是“能不能安全地给真实用户长期运营”的卡点。

| 卡点 | 为什么重要 | 进入公开 stable 前怎么解决 |
|---|---|---|
| Windows Authenticode 证书尚未接入 | Tauri updater 签名防篡改，但 Windows/SmartScreen 仍无法确认发布者信誉 | 购买/接入代码签名证书，签名并做时间戳，验证覆盖安装和 SmartScreen |
| 只有一台大陆 Windows 机器的网络样本 | 自定义域名一次可达不代表全国、不同运营商和校园/企业网都可达 | 至少覆盖电信、联通、移动和一个严格企业网，记录成功率、首包和完整下载耗时 |
| CI 仍是人工原型流程 | 人工步骤容易传错版本、签错包或先发布清单后上传文件 | 建立 staging 专用流水线；先 artifact、后签名、后草稿、冒烟通过后才 promotion |
| 签名私钥仍是原型级保管 | 密钥泄露等于攻击者可签合法更新 | 放入受审计 secrets/HSM 或隔离签名机；双人批准；设计轮换窗口 |
| macOS/Linux 尚未做同级端到端验证 | Windows 成功不能证明其它 bundle 的 updater 行为 | macOS 两架构完成签名、公证、安装；Linux 明确 AppImage/deb 的更新策略 |
| 控制面缺少生产级管理入口和审计 | 当前通过 Wrangler/D1 操作适合 staging，不适合多人长期运营 | 建立受 Cloudflare Access/服务令牌保护的管理面，记录操作者、前后值和审批单 |
| 监控、告警、备份与灾备未闭环 | 更新失败若无人发现，灰度就失去意义 | 加成功率/签名失败/下载失败监控，D1 导出与 R2 清单，演练恢复 |
| 中国大陆合规和长期网络路线未决 | 免费 Cloudflare 全球网络没有中国大陆本地 SLA | 内测先实测；规模扩大后评估 ICP + Cloudflare China Network，或国内对象存储/CDN 双源 |

## 4. 还需要用户或团队提供什么

内测原型阶段已经不缺必要信息；要进入下一阶段，需要以下组织性输入：

- Windows 代码签名证书的采购与保管方式。
- 第一批内测人员名单、设备上限、ring 归属和可接受的测试窗口。
- 是否把 CNB 作为 GitHub 镜像及 `primelab-win` 的 CI 调度入口。
- 正式发布时预计的设备数、每月更新频率和安装包平均大小，用于重新核算免费层。
- 是否计划申请 ICP/Cloudflare China Network，或同时准备一家大陆对象存储/CDN。
- 谁拥有“发布、扩大灰度、暂停、撤销、前向修复”的权限和最终审批责任。

## 5. 为什么现在不应该直接上线

原型证明的是技术闭环，而不是运营闭环。最危险的不是“下载失败”，而是一个签名正确但版本配错、灰度过快、无法及时止血的包。所以下一步应先把自动化、签名权限、网络观测和发布审批补齐，再让少量真实用户进入 canary。

在此之前，所有候选版本继续使用 prerelease 标识和独立 staging 域名；不建正式 tag、不更新官网、不修改公开 stable 清单。
