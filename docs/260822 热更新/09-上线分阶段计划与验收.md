# 09. 上线分阶段计划与验收

## 1. 总目标

在“下一个正式版本”中提供受签名、受兼容矩阵约束、可指定用户、可灰度、可暂停、可审计的 Desktop 一键更新；Runtime/UI 维持独立轨道。整个过程不拿现有线上用户做实验，先从专用 Windows 机器和邀请制 canary 开始。

## 2. 分阶段路线

### P0：技术原型（已完成）

- [x] Desktop↔Core 兼容矩阵进入代码和 CI 检查。
- [x] Tauri 官方 updater 替换自制壳安装逻辑。
- [x] Cloudflare Worker + D1 + R2 staging。
- [x] 设备 token、ring、确定性比例、Range、暂停。
- [x] `primelab-win` 从基线到候选的真实 UI 更新。
- [x] 暂停/0% 止血演练。
- [x] 线上版本、Landing、正式清单保持不变。

### P1：流水线和安全加固（建议 3–5 个工程日）

- 新增 staging 专用 CI，不触发公开 tag/Release。
- 接入 CNB 镜像和 Windows Build Node PoC，保留 GitHub 对照。
- 将 Windows 构建、OS 签名、Tauri 签名、上传、promotion 拆分身份。
- 创建 production Tauri 密钥，staging/production 信任根分离。
- 采购/接入 Windows Authenticode，验证时间戳。
- 实现受审计的 `create-draft/promote/set-percent/pause` 工具。
- 自动做 R2 完整回读、SHA、签名和兼容矩阵检查。

退出条件：任何人不能靠一次普通 CI job 直接构建并发布给 stable；所有候选默认只到 `draft, 0%`。

### P2：跨平台与大陆网络验证（建议 3–5 个工程日 + 网络采样时间）

- Windows：干净机、覆盖安装、代理网络、断网续传、磁盘不足、token 轮换。
- macOS arm64/x64：Developer ID、notarization、两架构安装和更新。
- Linux：明确 AppImage/deb 的产品支持范围；支持哪一个就对哪一个做真实更新。
- 网络：至少电信、联通、移动、企业/校园严格网络各一个样本。
- 记录 DNS/TLS/首包/完整下载耗时、Range、失败类别；验证自定义域名和备用域名。

退出条件：目标平台都有真实安装证据；大陆网络没有依赖 `workers.dev`；失败时应用仍正常启动。

### P3：邀请制 canary/beta（建议至少 1–2 周观察）

- canary 先 1 台，再 100%；稳定一个完整工作日后进入 beta。
- beta 按 5% → 25% → 100%，每档人工批准。
- 只邀请明确知情用户；每台设备独立 token，可随时禁用。
- 每档执行暂停演练和一个前向修复演练。
- 记录更新成功率、重新启动率、Core 启动率和网络分布。

退出条件：无数据丢失、无不兼容 Runtime、无签名绕过、暂停在预期时间内生效；安装失败都有可解释类别和人工恢复方法。

### P4：下一版正式 stable

- 先执行仓库 `desktop-release-preflight` 全套闸门。
- 正式安装包必须使用 production 签名、公证/Authenticode和 production 控制面。
- 国内镜像必须先有最终 artifact URL，再签任何把 URL 纳入载荷的 manifest。
- 先 production canary，再稳定扩大；不允许把 staging D1 记录直接改名为 stable。
- 只有正式 stable 资产和清单均存在后，才同步 Landing 和公开 `latest.json`。
- RC/beta/alpha/canary 永远不更新 Landing。

## 3. Go / No-Go 闸门

### 构建与版本

- [ ] Desktop/Core SHA 固定且工作树可复现
- [ ] Desktop↔Core↔Runtime 命中唯一兼容矩阵
- [ ] Runtime schema 在允许集合中
- [ ] 包内版本、D1 metadata、UI、注册表/Info.plist 一致
- [ ] 不使用 `latest` 作为最终物料标识

### 签名与供应链

- [ ] Windows Authenticode 或 macOS codesign/notarization 成功并可离线复核
- [ ] Tauri signature 针对 OS 签名后的最终文件
- [ ] R2 完整回读 SHA/size 与构建记录一致
- [ ] 私钥不在仓库、普通 runner、日志和 artifact 中
- [ ] staging/production 公钥与权限彻底分离

### 客户端与数据

- [ ] 无候选/控制面不可达不阻塞应用启动
- [ ] token 错误、ring 错误、paused、坏签名全部拒绝
- [ ] 更新后 Core 9120 正常，用户配置和会话保留
- [ ] 新内嵌 Runtime 不会覆盖磁盘上更高且兼容的 Runtime
- [ ] 配置/数据迁移支持前向修复，不依赖自动降级

### 发布与回滚

- [ ] 默认 draft 0%，promotion 需要独立审批
- [ ] 1 台 canary → 5% → 25% → 100% 可控
- [ ] pause 同时阻断新清单与 artifact
- [ ] 已下载/已安装设备的边界写入事故手册
- [ ] 已制作并实际演练一个更高版本号的前向修复

### 网络与运营

- [ ] 三大运营商和严格网络样本通过
- [ ] 不依赖 GitHub/`workers.dev` 才能检查和下载更新
- [ ] 监控能按 release ID 区分检查、下载、验签、安装、重启
- [ ] D1/R2 备份、库存和恢复演练完成
- [ ] 值班人员有 pause 权限和联系人清单

任一安全、签名、兼容、数据或暂停项未通过即 No-Go；不能以“先上少量看看”代替。

## 4. 建议观测指标

| 指标 | canary/beta 建议门槛 | 说明 |
|---|---:|---|
| 检查 API 成功率 | ≥ 99%（排除明确离线） | 按运营商/域名分组 |
| 授权下载完成率 | ≥ 98% | 允许用户主动取消单列 |
| Tauri 验签成功率 | 100% | 任何失败都暂停并查物料 |
| 安装器启动率 | ≥ 99% | 统计平台错误 |
| 更新后首次启动成功率 | ≥ 99% | 必须能关联 release ID |
| Core 启动与版本正确率 | 100% | 错版本立即停止灰度 |
| 用户数据丢失 | 0 | 一票否决 |

小样本阶段百分比容易误导，必须同时看每台设备的具体证据。

## 5. 成本预算

### 基础方案的现金成本

| 项目 | 内测期预期 | 备注 |
|---|---:|---|
| Cloudflare Workers/D1/R2 | 很可能 0 美元/月 | 在免费层内；必要时 Workers Paid 当前最低 5 美元/月 |
| CNB | 很可能 0 元/月 | 未超 100 GiB/100 GiB/160 核时；自托管节点不计平台核时，以官方当期规则为准 |
| `primelab-win` | 已有设备 + 电力/维护 | 专机减少安全隔离成本，不等于零运维 |
| Gitea | 基础方案不部署 | 若部署需另算云主机、DB、存储、流量、备份和人力 |
| Windows Authenticode | 待供应商报价 | 不写死金额；证书类型、硬件/云签名方式差异大 |
| Apple Developer/公证 | 使用现有账户或按苹果当期费用 | 需确认团队账户与证书权限 |
| Cloudflare China Network/国内 CDN | 内测期不采购 | Enterprise/ICP 或国内云按商务报价，beta 数据后决策 |

最大隐性成本是工程和运维，而不是当前 Cloudflare 流量。按单工程师估算，P1/P2 约 6–10 个工程日，P3 至少 1–2 周日历观察；证书采购、ICP 和跨地区测试可能成为外部关键路径。

## 6. 角色与权限

| 角色 | 负责 | 不应拥有 |
|---|---|---|
| 开发 | 代码、测试、兼容矩阵 | production promotion、签名私钥 |
| 构建维护者 | runner、缓存、可复现构建 | 设备名单、发布审批 |
| 签名维护者 | OS/Tauri 签名和审计 | 改源码、扩大灰度 |
| 发布负责人 | 审阅证据、promotion | 直接改签名产物 |
| 值班人员 | 监控、pause、事故协调 | 无审批的重新发布 |
| 安全/合规 | 密钥、证书、ICP、审计 | 日常修改版本 metadata |

小团队可以一人承担多个角色，但凭据和操作步骤仍要逻辑分离，关键发布至少双人复核。

## 7. 下一步的实际执行顺序

1. 合并本原型代码和文档前，完成人工代码审阅。
2. 新建 staging 专用 CI 配置，不改现有 tag release 工作流。
3. 在 CNB 建镜像并验证 Windows Build Node 可用性。
4. 接入 Authenticode，固定“OS 签名 → Tauri 签名”的流水线顺序。
5. 创建 production 密钥和资源，但保持无 stable 发布。
6. 补 macOS/Linux 目标平台端到端测试。
7. 招募第一批 canary，完成多网络采样和暂停/前向修复演练。
8. 所有 Go/No-Go 项通过后，才按正式发版技能处理下一版 stable。

## 8. 完成定义

“热更新完成”不是按钮出现，也不是 CI 绿灯，而是：一个被明确授权的设备能拿到正确版本，未授权设备拿不到；包在目标平台能通过双层签名、兼容检查和真实安装；发布方能分批扩大、迅速暂停、审计每次动作；出错后当前应用与用户数据仍可用，并能通过更高版本前向修复。
