## 2. 真实验收顺序

1. 创建新的 staging `.2 → .3` 或等价候选，不接触现有线上版本。
2. 注册 D1 `prototype draft, 0%`，核对 status 输出和 release_events。
3. 创建/确认 `primelab-win` device，promote prototype 100%。
4. 依次测 Cloudflare MISS/HIT/Range、GitHub fallback、错误 token、pause、坏签名。
5. 完成 Windows真实安装和数据保留核对，立即 pause/0%。
6. 用相同字节完成 macOS/Linux验证；任一平台失败不扩大。
7. 收集多网络样本，形成 go/no-go 记录。

## 3. 灰度节奏

| 阶段 | 范围 | 最短观察 | 推进条件 |
|---|---|---:|---|
| prototype | `primelab-win` 100% | 完整测试轮 | 全用例通过并回到 pause/0% |
| canary | 1 台 → 全部内部 canary | 至少 1 个工作日 | 无签名/安装/数据损坏；下载成功率达标 |
| beta | 5% → 25% → 100% | 每档人工批准 | 错误率和 fallback 在阈值内 |
| stable | 新正式 SemVer、production 签名重新构建 | 分档观察 | 通过正式发版权限和 Landing 同步 |

beta 记录不改名为 stable；stable 要重新构建，确保版本号、签名身份和公开语义一致。

## 4. 暂停与撤销

- `pause`：status=paused、0%，用于暂时止血，允许以后重新 promote。
- `revoke`：status=revoked、0%，用于明确否决该 release；不能重新 promote。
- 已下载但未安装的 pending 包在 install 前复核，因此 pause/revoke 能阻止它继续安装。
- 已安装用户不降级；发布更高版本前向修复。

## 5. 成功率指标

建议在内测期按 release/channel 聚合：

- check 2xx/204/401/5xx。
- Cloudflare 下载成功率、GitHub fallback 触发率和二次成功率。
- signature/SHA/size failure（任何一个都应为 0）。
- install-start 到新版本首次 check 的转化率。
- 安装后 Core 9120 启动成功率、Runtime 防降级结果。

建议自动 pause 条件：签名/SHA异常 1 次；安装后无法启动 >1%；配置/会话损坏 1 次；下载失败或 fallback 激增则人工研判网络后暂停。

## 6. 首个正式承重版本

现有用户的安装包没有完整的新 updater 控制契约，因此首个正式版本仍由用户手工覆盖安装。只有安装了该版本的用户，后续版本才进入自动更新。

承重版本必须同时包含：固定 identifier、production updater 公钥、Cloudflare control endpoint、系统凭据逻辑、兼容矩阵和 pending 恢复。上线前不能让官网 `latest.json` 指向任何 prototype/canary/beta。
