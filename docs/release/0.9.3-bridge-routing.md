# 0.9.3 过渡升级路由（本地准备）

旧版 0.9.0／0.9.1 → 0.9.3（Core 0.21.0-cn.19）→ 1.0.0（Core 0.23.0-cn.20）。采用私有桥接候选验证过的路由方式，扩展为按渠道、平台和架构分别登记正式过渡包。

更新服务增加可选环境变量 DESKTOP_093_BRIDGE_RELEASE_IDS，内容为 JSON 对象。键为 channel/target/arch，值为已登记的 release ID。需要 stable/windows/x86_64、stable/darwin/aarch64、stable/darwin/x86_64、stable/linux/x86_64、stable/linux-deb/x86_64 五项。Windows 便携版的手动覆盖升级另行验收。

配置启用后，所有低于 0.9.3 的版本（含 0.8.x、预发布及热修构建）仅查该路由的指定记录，继续要求同渠道、同平台架构、published 状态和灰度命中。版本必须为 0.9.3，Core 与 runtime 同为 0.21 且基础版本相同。记录缺失、暂停、撤销、灰度未命中或配置缺少路由时返回 204，不改发最新的 1.0。0.9.3 随后按正常最新记录获得 1.0。

变量尚未配置时保持既有行为。正式开放 1.0 之前，需要先登记五项正式 0.9.3 安装资产、完成各路由配置并验收；此变量随 1.0 上线持续保留，供晚升级用户使用。渠道不能共用不匹配的记录。生产配置与部署仍等待 Enzo 确认。

本地测试覆盖上述五条路由的两跳、不可用状态、Core 不匹配和灰度边界，更新服务测试文件共 13 项通过。此记录不等于线上已启用。


A7 二轮复核补充：无效 JSON、非对象或错误字段类型按无更新处理并记录配置错误，不能造成检查接口 500。按 SemVer 低于 0.9.3 统一选择过渡记录，不将其它旧版本直接引向 1.0。部署顺序为：先发布 0.9.3 并登记五条记录 → 配置映射 → 逐条用旧版本请求验证返回 0.9.3 → 再公开 1.0 stable，按既有确认边界执行。

整包服务的客户端版本来自 /v1/check URL；X-Hermes-Desktop-Version 属于官网 /runtime 组件路由。尝试读取生产 D1 的版本事件时，本会话没有可用 Cloudflare API_TOKEN，尚未取得线上分布。更旧版本均已纳入路由测试；若后续证实某一历史外壳拒绝 0.9.3，则单独为它返回 204。

/runtime 的 cn.19 只提供给 0.9.2 及以后外壳，由官网组件路由维护；此项需要在该工作树单独核对。整包桥路由不替代组件路由。
