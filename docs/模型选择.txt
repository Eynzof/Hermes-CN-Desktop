聊天框选了 deepseek 实际调用 claude，API key 频繁失效，新用户重新登录后 apikey 不刷新。

 排查后确认这不是三个独立 bug，而是模型来源没有统一所有者导致的连锁故障。当前 workbuddy 分支上有 4 个已证实的根因：

 R1 —内置模型完全没有写入方。
 custom:<BRAND.providerKey> provider 在本分支上没有任何代码创建或刷新。做这件事的 src/commands/account.rs（8
 个命令：登录 newapi →/api/token 取 sk- key →写 provider，key 存 keyring）只存在于 huanxing
 分支（665024c），从未合入。commit 48b54c7 把 huanxing-auth.ts 删掉 196 行后，登录只剩 auth-dialog.tsx:48 的
 setAccount(account) →写进 ui-store，再无下文。
 ensureBrandProviderModelDeclared（provider-catalog.ts:1356）自身注释就写着 "never creates a provider or invents
 credentials"，缺条目时直接返回原 config。src/brand_generated.rs:8 的 BRAND_PROVIDER_KEY 在整个 src/ 里零消费者。
 →用户 config.yaml 里的 custom:fengchihermes 只可能是旧版 huanxing 构建残留的遗留条目，里面的 api_key 属于上一个用户 /
 上一次装机，登录、换账号、登出都不会碰它。这就是「api key 失效」和「新用户登录后 apikey 没刷新」的完整解释。

 R2 —team_sync.rs 用裸字符串覆写整个 model: 映射。
 src/team_sync.rs:180-195 执行 map.insert("model", format!("custom:team-{}", default).into()) ——插入的是 YAML
 标量字符串，且值是一个 provider id 而非模型名。
 Core 的 _get_model_config()（hermes_cli/runtime_provider.py:298）对标量走 return {"default": model_cfg.strip()}，丢弃
 provider / base_url / api_key。
 于是企业同步后全局默认模型变成字面量 "custom:team-glm-5-2"，provider
 上下文全失。任何回落到全局默认的会话都会拿这个垃圾值进 Core 的猜测链路 →落到能找到凭证的 provider（通常是
 anthropic/claude）。这是「选 deepseek 实际调用 claude」最直接的一条路径。

 R3 —provider 标识三套不一致，含点的 id round-trip 必然失败。
 - Core model.options 对 providers: map 条目发配置键原样（model_switch.py:2553），对 custom_providers:
 列表条目发显示名派生的 slug（custom_provider_slug，providers.py:683）。
 - 桌面端 normalizeProviderIdForGateway（web/src/lib/provider-id.ts:7）在 slug 剥掉 custom: 后含点时把前缀丢掉。
 - resolve_user_provider（providers.py:657）按精确配置键查，raw 已被 lower（providers.py:785）但 Core 发出的键没有
 lower。

 结果：custom:team-glm-5.2、custom:team-kimi-k2.6 这类含点 id 发出去变成 team-glm-5.2，Core 精确键查不到 →走
 resolve_custom_provider 显示名匹配 →也不中 →pdef is None。同理配置键含大写时必挂。

 R4 —企业模型有两个互不清理的写入方。
 src/team_sync.rs:125 写 custom_providers: 列表（按 team_managed: true 清理，硬编码 api_mode:
 chat_completions）；web/src/lib/enterprise-sync.ts:149 写 providers: map（按 custom:team- 键前缀清理，区分
 anthropic/openai）。两者清理条件不相交，互留残骸 →重复条目 + 陈旧 base_url/token 长期存活。

 另需堵死的静默路径：ComposerModelSelection.provider 是可选的（composer-types.ts:32）。为空时
 buildGatewayModelConfigValue 发出裸模型名，Core 走 PATH B 静默猜 provider（DIRECT_ALIASES 按 model id 反查 →
 model_switch.py:745，命中后 1580-1588 还会用 alias 的 base_url 覆盖端点并把 api_key 置成 "no-key-required"）。PATH A
 的 pdef is None 是唯一硬失败，PATH B 没有对应保护。

 目标：三类模型（内置=serviceUrl 账号 / 自定义=用户自填 baseUrl / 企业=设备令牌下发）收敛到一套 provider
 标识、一个写入方、一条凭证刷新路径，且模型切换不再可能静默改道。

 已确认的设计决策

 1. 内置模型 →移植回 Rust account.rs，sk- key 存 OS keyring，只有 masked 值过 IPC。
 2. 标识统一 →只改桌面端，不动 Core。因此必须迁就 Core 现有解析规则，而非期待 Core 变。
 3. 范围 →统一抽象，一次做完三类模型。

 设计

 канонprovider id 规则（唯一）

 因为只改桌面端，必须让三个标识函数对同一个值产生相同结果。做法是让配置键落在 Core 三条解析路径的交集里：

 - 一律写进 providers: map，永不写 custom_providers:（这样 Core Section 3 原样回发配置键，resolve_user_provider
 精确命中）。
 - 键格式：custom:<ns>-<slug>，其中 ns ∈{acct, team, user}。
 - slug 规范化：转小写 →[^a-z0-9_-]（含 .）替换为 - →合并连续 - →去首尾 -。

 这条规则同时满足：不与 Core 内建 slug 撞（custom: 前缀）、不触发 normalizeProviderIdForGateway
 的剥点逻辑（无点）、大小写安全（全小写）。

 命名空间：

 ┌────────┬──────────────────────────────────────────────────────────────────────────┐
 │  类别  │                               provider id                                │
 ├────────┼──────────────────────────────────────────────────────────────────────────┤
 │ 内置   │ custom:acct-<brandProviderKey> / custom:acct-<brandProviderKey>-messages │
 ├────────┼──────────────────────────────────────────────────────────────────────────┤
 │ 企业   │ custom:team-<sanitized model id>                                         │
 ├────────┼──────────────────────────────────────────────────────────────────────────┤
 │ 自定义 │ custom:user-<sanitized host 或名称>                                      │
 └────────┴──────────────────────────────────────────────────────────────────────────┘

 分类从此是纯前缀判断，取代 model-provider-visibility.ts 现有的三路启发式（team_managed / token_id / 品牌 id 集合）。

 单一写入方：src/model_registry.rs（新增）

 Rust 独占所有 managed provider 的 config 写入。理由：内置的 key 不能过 IPC（keyring 在 Rust）、企业同步已在
 Rust、避免两套 merge 实现再次漂移。

 核心函数 apply_managed_providers(config, desired: &[ManagedProvider]) -> Config：
 - 只接管匹配 ^custom:(acct|team|user)- 的键；不在 desired 里的删除，在的upsert。
 - 不触碰任何其他 provider（用户手写的、Core 内建的）。
 - 迁移：把 custom_providers: 列表里带 team_managed: true 或旧 custom:team-* 的条目移出并转成 map 条目。
 - model: 只写映射，永不写标量，且 model.default 只放模型名、model.provider 只放 provider id。

 复用现有 src/team_sync.rs 的 atomic_write（team_sync.rs:86）做落盘。
